# Living Sector — опорные точки Godot и маршрут разработки

**НОВОЕ РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ (12.11.2026, применяется ко всем пяти автоматическим сменам):** каждый запуск берёт **один крупный, содержательно связанный блок** из оригинального Rust, предварительно атомарно резервирует **один свободный Nx**. Не требуются три разных Nx, три claims и три PR. Один большой блок может охватывать много связанных файлов, функций и задач. Если блок не завершён в одну итерацию, сохранить реальные коммиты и оставить `IN_PROGRESS`; новый Nx брать только после завершения первого и нового резервирования. Старые правила ниже про обязательные «3 блока» отменены. Проверки минимальные; фазы переноса/сборки/Grok прежние. Обновлены инструкции пяти плановых задач.

## Согласованный трёхфазный план и команда «Дальше» (12.11.2026)

**Фаза 1 — ТЕКУЩАЯ: полностью перенести ВСЕ уже существующие механики, формулы и состояния замороженной Rust Galaxy 0.6.7 в Godot/GDScript.** Закрытие фазы определяется полнотой исходного поведения, а не количеством созданных Nx и не процентом GitHub PR. По возможности сделать инвентаризацию незакрытых Rust-механик и избегать дублирования работы.

**Фаза 2 — ПОТОМ:** собрать весь перенесённый код в **один** Godot-проект: единый игровой цикл, подсистемы, интерфейс и сохранения; после сборки провести сквозное тестирование и устранить ошибки работоспособности. До этого фазу интеграции ради промежуточных проверок не форсировать.

**Фаза 3 — ПОСЛЕ ФАЗЫ 2:** дополнительные правки и улучшения, предложенные Grok. Не подменять ими исходные Rust-правила и не начинать фазу 3 преждевременно.

**Ручной рабочий чат:** сообщение пользователя **«Дальше»** означает взять **один КРУПНЫЙ свободный компонентный блок**, сначала атомарно зарезервировать его в общей координационной ветке через `claims/Nx.json`, указать владельца, границы файлов и зависимости, затем реализовать перенос из Rust с PR/исходниками. При необходимости крупный блок допускает несколько внутренних задач, но не дублирует чужой Nx. В конце каждого такого ответа дать понятный короткий итог и **примерную долю работы по ФАЗЕ 1, которая ещё осталась (в процентах)**. Это символический экспертный ориентир, число может уточняться; считать по покрытию механик, а не по номеру N. Не смешивать с 3 резервированиями на запуск в отдельных автоматических сменах.

**Проверки:** на фазе 1 только необходимые быстрые самопроверки кода/формул, без циклов полных Godot-тестов и без просьб к пользователю запускать Godot. Текущая Godot P1 сохраняется как неподвижный контрольный снимок. Промежуточные результаты обозначаются `CODE_UNVERIFIED` до реального запуска.


## Утверждённая стадийность переноса (12.11.2026)

**Главная задача сейчас — полный перенос оригинальной Rust Galaxy 0.6.7 по самостоятельным компонентам.** Сначала покрыть оставшиеся механики, формулы, сохранённые данные и ИИ (в том числе строительство, колонизацию, производство, научные цепочки и управление фракцией), сверяясь с Rust и уже написанными PR; не расширять план бесконечной серией инфраструктурных/тестовых Nx. На текущей стадии **не требуются** интеграция каждого блока в P1, повторяющиеся end-to-end тесты, отладка движка без запуска или ZIP для пользователя. Принимать CODE_UNVERIFIED с минимальной самопроверкой синтаксиса/контрактов как промежуточный результат.

**Только после покрытия всего исходного функционала** — собрать компоненты в один Godot-проект, согласовать единый TickRunner и атомарный сохранённый world state, провести общую интеграционную приёмку и уже затем просить пользователя запустить Godot один раз для обнаружения и исправления фактических ошибок. Это **не отменяет** точные Rust-инварианты, исходники, резервирование claims, запрет недоказанных механик и сохранность контрольной P1.

**Все 5 запланированных смен:** три отдельных Nx за запуск, сначала три атомарных резервирования, затем реализация по очереди с PR и честным статусом. Если предыдущие инструкции требуют отдельных headless smoke-тестов по каждой N-задаче, ручного запуска после 20–30 блоков или немедленного слияния с P1, действует **эта более новая стадийность**.


**Статус: 12.11.2026.** Этот документ дополняет и при расхождении фактов о **первом запуске Godot, кодовой базе и порядке проверок** имеет приоритет над устаревшими введениями NIGHT_SHIFT_QUEUE_RU.md / NIGHT_SHIFT_LOG_RU.md. Протокол claims и замороженный Rust-эталон сохраняются без изменений.

## Политика тестирования и передачи пользователю

- **Пользователь готов к Windows проверке лишь раз в ~20–30 завершённых этапов/задач**, а не после каждого PR/малой ошибки. Внутри разработки выполнять короткие статические проверки, локальный Godot --headless (если реально доступен), тесты инвариантов и компактный приемочный сценарий. Если Godot Runtime отсутствует, честно `CODE_UNVERIFIED`, не перекладывать запуск отдельных 11 тестов на пользователя.
- Пользователь получает **один полный ZIP от проверенной интеграционной ветки**, один `PLAY-LIVING-SECTOR-WINDOWS.cmd` или аналог, автоматическую запись итогов/логов и минимум ручных действий. Ни отдельных .cmd-патчей, ни перекладывания пары исходников, ни десятков отдельных проверок.
- Вехи не заменяют внутреннее тестирование. Досрочный запуск у пользователя запрашивать только если действительно блокируется крупный интеграционный этап и нельзя заменить его доступной агентской проверкой.
- Исключить из автоматических smoke запись в пользовательские реальные `user://saves`; тестовые сохранения должны иметь собственный путь и убираться.
- Ручное подтверждение интерфейса — не доказательство работающей экономики. Названия статусов: `CODE_UNVERIFIED`, `STATIC_CHECKED`, `WINDOWS_UI_VERIFIED`, `RUNTIME_MECHANICS_VERIFIED`, `RUST_PARITY_VERIFIED` — с конкретным доказательством.

**Важно:** этот документ не меняет расписания автоматических задач сам по себе и не останавливает работающий чат. Для новых чатов давать ссылку на него; плановая задача должна читать его при каждом запуске.
