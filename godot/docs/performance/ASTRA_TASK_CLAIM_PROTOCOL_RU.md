Проверяй более подробные пункты своего направления выше по тому же документу и уже закрытые claims. Никакой новой «очереди вместо Астры», повторения исправленных мест или работы над одними handoff.

**Единственная рабочая ветка:** `integration/perf-astra-5-workers-20261116` (PR #262). Пять активных почасовых воркеров A–E работают на ней непосредственно. Бывшие recovery/verified ветки — только архив. PR #272–#275 уже портированы с тестами в эту ветку коммитом `f76a7e6df0d1cedbe2b75c2b7bf05a28dae2a6ba` (без исполнения тестов); не переносить их повторно, не запускать старые recovery задачи. Не редактировать SystemBalance, main, stable, чужие файлы и не выполнять Actions.

**При каждом ЧАСОВОМ запуске ожидается один существенный и завершённый блок реализации из незакрытого пункта плана Астры — не один небольшой рефакторинг ради отчёта.** Обычный масштаб: проработанный горячий путь с несколькими взаимосвязанными изменениями в реальных source-модулях/вызовах, корректной интеграцией и targeted positive+negative/oracle regression. Для крупного пункта выбирай логически завершённый подэтап, например замену одной повторно выполняемой операции во всех нужных callsites с сохранением invalidation/rollback и тестом. Не задавать искусственную норму строк, не раздувать патч ненужными правками и не брать чрезмерный риск ради объёма. Если после первого маленького исправления задача ещё не стала существенным блоком, доделай недостающие связанные части или возьми следующий совместимый подэтап в том же направлении. «Добавил тест», «добавил лог», «обновил claim», «поменял одну строку без end-to-end охвата» — сами по себе НЕ полноценная смена.

### Цикл «ВЗЯЛ → РЕАЛЬНЫЙ КОД → СДЕЛАЛ» на КАЖДОМ запуске

1. Сверь актуальный HEAD PR #262, список Астры, историю коммитов/claims и границы файлов A–E. Выбери **самый следующий свободный осмысленный пункт** своего направления, не заменяя исходный backlog новой инициативой. Перед первым редактированием игрового кода атомарно создай уникальный `godot/docs/performance/claims/<task-id>-<role>.md` с `STATUS: IN_PROGRESS`, ID/цитатой пункта Астры, ожидаемым большим результатом, перечнем реальных файлов, рисками, SHA старта, временем и owner. Если claim занят — следующий свободный.
2. **Сразу после claim писать код**, не уходить в многочасовые обсуждения и перепроверки. Исследуй конкретные callsites, устрани повторные копии/обходы/неэффективную операцию на *исполняемом* пути, в нужных местах адаптируй вызовы/кеш-invalidation/ownership, дополни targeted тесты на нормальное и ошибочное поведение и строгий comparator старого алгоритма. Прямо сохраняй Rust-поведение, World, N9, N38, BT/RNG, деньги/поставки/маршруты, порядок, exact replay. Для C/D — никаких перемещений/рынков без реальных контрактов/ресурсов; для E — полноценный работающий инструмент профиля/проверки, не декоративная метрика.
3. Подключённый GitHub API достаточен для исходников и тестов без локальных Git/Godot. При каждом update_file брать свежий blob SHA; не перетирать параллельные коммиты, не force-push. Не трогать чужую область даже ради быстрого выигрыша; при пересечении оформить нужную доработку для её владельца, а самому продолжить независимую задачу.
4. Закончив кодовый блок, обнови ТУ ЖЕ claim: `STATUS: CODE_DONE_TEST_UNVERIFIED` или `VERIFIED` лишь после настоящего исполнения, SHA исходников и теста, охваченные callsites и реальный эффект изменения, проверенные условия/отрицательные случаи, TEST PASS/FAIL/NOT_RUN, неохваченный риск и **следующий конкретный пункт Астры**. При реальной блокировке — `BLOCKED` с инструментом/ошибкой и шагом восстановления, не выдавать анализ/документы за успешную разработку.
5. При наличии времени переходи к следующему независимому подэтапу через новый claim. **На следующем часовом запуске продолжай там, где остановился**, не перезапускай одно и то же исследование и не допиливай бесконечно мелочи предыдущего исправления. Цель: накопленный существенный объём безопасных оптимизаций для утреннего Windows теста, а не максимальное число commit/claims.

**Минимальный отчёт за каждый запуск:** ROLE; ASTRA пункт и его подэтап; CLAIM; CODE SHA; реальные изменённые source-функции/callsites; TEST SHA и PASS/FAIL/NOT_RUN; что улучшено/какие сохранены инварианты; NEXT пункт Астры. Если кодового SHA нет — явно `NO_CODE`, назвать точный технический блокер; не писать `DONE`.

**Проверки:** GitHub Actions вообще не запускать до отдельного решения пользователя. Новые изменения до Godot/Windows — `CODE_UNVERIFIED / PERFORMANCE_NOT_MEASURED`. Не делать автоматический merge в другие ветки. Замеры выполнить позже на одинаковом seed/версии: оплаченные тики 100/300/600/900+, phase avg/p95, память, full World/N9/BT/RNG/N38 parity, save/restart, negatives.

### Направления (подробные пункты брать ИЗ ПЛАНА АСТРЫ, не из этого резюме)

- **A:** N39 snapshot L129/L196, локальные owned writes/rollback, оптимизация Schema/validators без пропуска full oracle.
- **B:** N9 транзакционные overlay/receipt/provenance, рост history, совместимый N38 save/restart и точное сохранение отчётности.
- **C:** N84/N140 ship/BT, флот/маршруты/контракты/доки; индексы и детерминированная инвалидизация без изменения физики.
- **D:** фактические повторные обходы Head/factions/stations/markets и event queue; одинаковые решения, цены и порядок событий.
- **E:** реальный N158 paid-tick измерительный контур, bounded сравнение ранних/поздних окон, измеряемый overhead, parity harness; не возвращаться к уже готовому worker/UI.

У всех пяти одна общая ветка и пять непересекающихся областей владения. Сохранять #262 draft, не ослаблять проверку корректности и не объявлять прирост скорости без реального A/B замера.
