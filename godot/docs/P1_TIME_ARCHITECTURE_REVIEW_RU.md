# P1 — решение по игровому времени: НЕ копировать Rust 8-TPS архитектуру без пересмотра

**Ревизия:** 12 ноября 2026. **Статус:** техническое предложение для архитектурного P1-блока, **не реализовано и не проверено в Godot**. Код `clock.gd` и `tick_runner.gd` из PR #87 служит **временным эталоном поведения Rust**, а не окончательной архитектурой развития на 1000 игровых лет.

## Зачем пересмотреть именно сейчас

В Rust `TickConfig` установлен на 8 тиков/с и `world_speed = 0.25` по умолчанию. `world_speed / TPS` масштабирует скорость движения и расчётов; нативные подсистемы включаются на разных кратных тиках `tick_multiplier`. Это рабочий вариант для реального сервера, но **не обоснование, что 8 глобальных тиков/с оптимально для автономной игры с тысячами кораблей и 1000-летней перспективой**.

У Godot есть штатные `_physics_process(delta)` с фиксированной частотой (по умолчанию 60/с), `_process(delta)` с кадровой частотой и [Physics Interpolation](https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/physics_interpolation_introduction.html). **Не путать этот физический цикл с экономическим календарём.**

## Рекомендуемый кандидат: гибридный симуляционный календарь

1. **SimTime** — один монотонный счётчик игрового времени, `world_speed` меняет скорость прохождения игрового времени. Для детерминизма — целые единицы времени, а не сумма плавающих `delta` без контроля ошибок. Godot engine.time_scale **не использовать** как единственное игровое ускорение: он влияет также на движковые таймеры/анимации, что может задевать UI.
2. **Scheduler / priority queue** — ближайшее реальное событие по (`due_time`, `phase`, `entity_id`, `sequence`). События: прибытие корабля, окончание производственного цикла, зарплатная выплата, изменение контракта, завершение исследования. Порядок одинаков при обычном и ускоренном запуске. Одна и та же операция никогда не применяется дважды.
3. **System cadence** — не всё рассчитывается 8 раз/с: физический прогресс редких объектов или тиковые движения там, где нужны, рынок/производство по реальным периодам или событиям, население — на своём более редком календаре, Director и администраторы — по расписанию **или** в ответ на кризис/значимую смену состояния. Конкретные игровые периоды определяем из исходных Rust значений, не придумываем заново до аудита.
4. **Предсказуемая кинематика** — для корабля, следующего по подтверждённому маршруту без взаимодействий, положение вычисляется из текущего сегмента и игрового времени. Груз, докинг, топливо и контракт обновляются **только** в фактических фазах/событиях симуляции. Для интерактивных действий/стыковок возможен отдельный частый локальный обновитель.
5. **Presenter / Rendering** — Godot Camera2D, CanvasItem/MultiMesh и штатная интерполяция для подходящих Nodes, собственная визуальная интерполяция двух истинных снимков для массовой пакетной отрисовки. Визуальные кадры не могут менять SimWorld.
6. **Fast forward ×16 и дальше** — обрабатывать события до целевого игрового времени хронологически, с лимитом работы за кадр и продолжением на следующих кадрах, чтобы UI оставался отзывчивым. **Не пропускать финансовые/ресурсные транзакции простым умножением результата**, когда возможен дефицит, конкуренция за деньги/ресурс и изменение стратегии. Возможность математически группировать интервалы рассматриваем позднее и только при доказанном сохранении инвариантов.
7. **Сохранения** — serializable SimTime, календарь событий, deterministic sequence, планы и текущие агентские состояния; после load событие с сохранённым ID не должно оплачиваться или исполняться второй раз. Текущий P1 checkpoint v1 хранит только орбитальные углы и не является заменой будущему формату.

## Сопоставление архитектур

| Подход | Плюсы | Минусы | Решение |
|---|---|---|---|
| Rust 8 TPS / полный проход всех фаз | Простой паритет, воспроизводимость | Много пустых обновлений, масштабирование времени зависит от TPS, неудобно для столетий | Оставить **эталонным сценарием**, не финальной архитектурой |
| Всё в Godot `_physics_process` (60 TPS) | Бесплатный fixed timestep/interpolation | Ненужные пересчёты экономики/ИИ, зависимость от физического цикла, объём кадровых работ | Только когда физика/перемещение действительно того требует |
| Только event-driven, без фиксированных фаз | Быстрый переход больших интервалов | Сложнее при насыщенных конкурентных действиях и непрерывных взаимодействиях | Не использовать как догму |
| **Гибрид: SimTime + events + частоты + snapshots** | Подходит тысячам агентов и большим временным интервалам, ясное разделение | Требует версионированного scheduler и тестов эквивалентности | **Предпочтительный кандидат для следующего архитектурного эксперимента** |

## Что делаем с готовым PR #87

- **Не удаляем** `clock.gd`, `tick_runner.gd` и тесты: это полезный лёгкий тест базовых формул и переноса орбит.
- **Не связываем P2/P3 production, logistics и AI** напрямую с `_advance_one_tick()`, пока не принят общий календарь и вариант scheduler.
- В первой следующей итерации — 3 связанные задачи: `SimTime` + детерминированные события (одинаковые timestamps / tie-break), пример одной орбиты и одного запланированного события, сравнение с 8 TPS на ограниченном сценарии; только после этого выбирать финальное API.
- Нужны два режима: **live/visual** и **headless fast-forward**, **одинаковая игровая логика**, а не два разных движка.
- Изменение сроков процессов/экономических формул **запрещено без отдельного баланс-решения**; менять реализацию времени не значит менять игру.
- Перед интеграцией нужны 3 коротких теста: независимость результата от FPS, одинаковый результат при ×1 и ×16 на одном количестве игровых часов, save/load без повторной выплаты и ошибки порядка событий.
- Следить за возможным `tick_multiplier == 0` в старой Rust формуле `round(TPS/world_speed)` при некоторых комбинациях низкого TPS и высокого world_speed: никакого деления по модулю 0.
