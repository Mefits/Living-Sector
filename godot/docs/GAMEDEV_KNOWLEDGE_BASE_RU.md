# Living Sector — постоянная база решений по геймдеву

**Цель:** перед тем как писать новую механику, искать готовый **проверенный приём** и пользоваться возможностями Godot. Ссылки и короткие правила хранятся в GitHub; ни одна внешняя статья не считается автоматически применимой или внедрённой.

## Быстрый справочник: симптом → готовый приём

| Проблема | Сначала проверить | Избегать |
|---|---|---|
| Корабли двигаются рывками | Physics/render interpolation; отдельно Camera2D smoothing; [руководство](SMOOTH_MOTION_RU.md) | Tween на каждом тике для исправления настоящих рывков |
| Движок лагает при тысячах объектов | Custom CanvasItem draw, MultiMeshInstance2D, RenderingServer, Profiler, LOD/culling | 10 000 отдельных сложных сцен с собственным _process без измерений |
| Галактическая карта/камера неудобна | Camera2D, CanvasItem, InputEventMouseMotion, Tween; для сложных режимов Phantom Camera | Переписывать кинематографическую камеру с нуля |
| Нужно огромное дерево технологий | GraphEdit/GraphNode/GraphFrame, сигнал on_connect_request, виртуализация по веткам | Самодельный HTML/JS граф внутри игры без нужды |
| NPC постоянно меняет направление | State machine/BT, минимальное время коммита, hysteresis; LimboAI/State Charts для инструментов | Менять план каждую _process секунду при колебании веса |
| ИИ «производит» ресурсы без товара | Command + Event Queue + строгое подтверждение транзакции/receipt | Считать успехом намерение/прогноз вместо native-эффекта |
| Нельзя восстановить сейв | Версия данных, атомарное сохранение, журнал операций, save/load parity | Сериализовать всю сцену и надеяться на корректный reload |
| Трудно найти причину тормозов | Godot Profiler + Monitor; замеры TPS/FPS/allocations по фазам | Оптимизировать всё подряд и запускать часы ненужных тестов |
| Нужно сгладить progress bar/панель | Tween, Theme, ProgressBar, AnimationPlayer | Привязывать UI-анимацию к изменению реальных ресурсов |
| Нужно приложение без компиляции Rust | Godot Standard portable, Git update + запуск сцены, headless CLI, Export Templates | Собирать движок из исходников ради каждого изменения |
| Внешняя библиотека тормозит / ломает экспорт | Проверить поддерживаемый движок, license, GDExtension binaries, minimal test | Ставить все плагины из AssetLib и считать их бесплатными по производительности |

## Небольшой перечень паттернов, нужных конкретно нашей игре

1. **Game Loop + fixed-step:** экономика и AI тикают последовательно, FPS не меняет смысл операции.
2. **Command + Event Queue:** UI/Head/Ship формируют запрос; отдельная фаза валидирует и применяет его точно один раз.
3. **Double Buffer:** старый/новый снимок состояния, одновременно прочитанная информация для многих агентов, плавная визуализация.
4. **Observer / signals:** UI получает уведомления об изменении среза состояния, но не владеет бухгалтерией.
5. **State / Behavior Trees:** для исполнения конечных решений кораблей и локальных задач; стратегические модели и ресурсный оптимизатор — отдельно.
6. **Spatial Partition / Data Locality:** раздельный поиск и обновление видимых кораблей; на сцене не обязательно размещать все 10 000 объектов.
7. **Dirty Flag:** пересчитывать дорогой список/окно только при изменении источника, не на каждый кадр.
8. **Object Pool:** только если замеры показывают частые аллокации с заметной ценой. Крупные immutable Resource справочники можно переиспользовать.

Все восемь описаны в [Game Programming Patterns](https://gameprogrammingpatterns.com/contents.html), но **это справочник решений**, а не требование реализовывать восемь отдельных фреймворков.

## Шаблон предварительного инженерного решения

Перед созданием новой системы фиксируем в PR:

- **Задача и текущий источник Rust:** какие реальные функции/формулы/инварианты сохраняем?
- **Тип проблемы:** отображение, симуляция, путь, UI, данные, тест, сохранение?
- **Встроенный Godot механизм:** какие конкретно классы/методы доступны, ссылки на docs.
- **Сторонняя альтернатива:** рабочий upstream, license, версия, совместимость Godot 4.7, экспорт Windows.
- **Почему выбран этот путь:** стоимость интеграции, производительность (для больших чисел), простота локальной диагностики, можно ли удалить плагин без переписывания экономики.
- **Как проверить:** один короткий сценарий; что считается выполненным, какие требования пока не проверены.
- **В трекер:** VERIFIED только при реальном тесте; CODE_UNVERIFIED при написанном коде.
