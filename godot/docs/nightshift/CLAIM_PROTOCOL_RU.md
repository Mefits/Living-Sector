# Параллельные чаты: протокол резервирования рабочих блоков

**Этот файл обязателен для ВСЕХ агентов и чатов**, включая обычный интерактивный чат и часовую автоматизацию. Один общедоступный координационный адрес: ветка **`feature/godot-nightshift-20261112`**, каталог **`godot/docs/nightshift/claims/`**.

## Резервирование ДО начала разработки

1. Читать самую свежую [очередь](../NIGHT_SHIFT_QUEUE_RU.md), [журнал](../NIGHT_SHIFT_LOG_RU.md) и содержимое [claims/](claims/). Подходящими являются блоки `TODO` или явно свободные. **Наличие файла `claims/N3.json` — признак занятого/уже рассмотренного N3 вне зависимости от устаревшей пометки в таблице.**
2. Выбрать блок `N1`…`N8`, не занятый другим чатом. **Самым первым действием записи в GitHub сделать `create_file` пути `godot/docs/nightshift/claims/Nx.json` именно в общей ветке** (а не в личной рабочей ветке). Вызов с уже существующим файлом должен завершиться ошибкой. Не использовать `update_file` на чужом claim.
3. Заполнять claim **до начала исследования, кода и тестов**: ID блока, `status: IN_PROGRESS`, `owner: overnight-scheduler | interactive-chat | other-agent`, уникальный `run_id` (время/название запуска), время начала ISO 8601 (с timezone), источник branch/SHA, планируемая рабочая ветка, ожидаемые 3–5 крупных задачи.
4. **Только после успешного create_file** немедленно обновить строку этого блока в [NIGHT_SHIFT_QUEUE_RU.md](../NIGHT_SHIFT_QUEUE_RU.md) на `IN_PROGRESS`, добавить начало в [NIGHT_SHIFT_LOG_RU.md](../NIGHT_SHIFT_LOG_RU.md). Если запись таблицы не удалась из-за изменения SHA, **повторно прочитать файл и аккуратно обновить строку**, сохранив чужие записи. **Claim уже достаточен для эксклюзивного владения**, даже если таблица пока отстаёт.
5. При конфликте `create_file` (409/422/конкурентное обновление Git): НЕ продолжать работу над Nx; перечитать актуальные claims + очередь и попробовать следующий `TODO`. **Не использовать force push или update_file поверх чужого claim для захвата.**
6. Начать код **только в собственной рабочей ветке** от последней корректной Godot-ветки. Одинаковая координационная ветка используется обоими чатами **лишь для claim/очереди/журнала**. Перед созданием новой ветки посмотреть, не изменил ли другой чат зависимости и важные файлы. Перекрывающиеся изменения согласовать через отдельные PR.
7. Завершая блок: написать реальный commit/PR и тест/доказательство; обновить **собственный** `claims/Nx.json` на `CODE_UNVERIFIED`, `VERIFIED` либо `BLOCKED` с SHA, ссылками, точным перечнем проверок и препятствий; обновить строку очереди + журнал. **Закрытый claim остаётся как история**, не удаляется.
8. Если выполнение не завершилось: оставить `IN_PROGRESS` с указанием текущего SHA/причины или `BLOCKED`. Вторая сессия **не имеет права молча отбирать** это направление. Перераспределение/снятие зависшего claim — только по явному согласованию пользователя либо аккуратной передаче владения с сохранением истории в PR; не основывать автоматический steal на таймауте.
9. Каждый запуск должен проверять актуальные статусы **с сервера GitHub**, а не полагаться на память предыдущей беседы. Если завершить нечего/все блоки заняты, сообщить об этом и сохранить собственный run-report, **не создавать параллельную реализацию той же фазы**.
10. Итог всегда содержит строку **«Текущее состояние»** — P0/P1/P2/100 VERIFIED, отдельно написанное/не проверенное, занятые Nx, ссылка на PR.

## Приоритет достоверности статусов

**При выборе блока порядок истины:** `claims/Nx.json` > текущий серверный GitHub PR/commits > `NIGHT_SHIFT_QUEUE_RU.md` > `NIGHT_SHIFT_LOG_RU.md` > старый контекст чата. Противоречия фиксировать отдельной записью и исправлять без потери чужой информации.

## Почему отдельный файл на блок

Изменение общей Markdown-таблицы не является надёжным «замком»: два чата могут одновременно выбрать один `TODO` до публикации статуса. Первое создание **одного и того же GitHub пути** без existing-file SHA позволяет разрешить гонку. При сетевом или GitHub-конфликте исходное состояние надо перечитать. Эта схема работает только если **оба чата используют одну и ту же общую ветку и правила**; это не заменяет гарантию распределённой транзакции, но предотвращает обычное двойное резервирование.

## Формат примера

```json
{
  "block_id": "N3",
  "status": "IN_PROGRESS",
  "owner": "overnight-scheduler",
  "run_id": "2026-11-12T03:55:00+03:00-overnight-3",
  "claimed_at": "2026-11-12T03:55:00+03:00",
  "coordination_branch": "feature/godot-nightshift-20261112",
  "source_sha": "actual fresh GitHub HEAD",
  "work_branch": "feature/godot-nightshift-n3-events",
  "tasks": ["cadence", "event queue", "short deterministic test"],
  "progress": [],
  "evidence": []
}
```

Это **пример структуры**, не реальное резервирование. До фактического запуска файлы `claims/N1.json`–`N8.json` должны отсутствовать.
