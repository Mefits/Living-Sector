# Аудит архитектуры времени: решения Factorio, RimWorld, Paradox и источник SpaceProjectSim

> **РЕШЕНИЕ P1 / 12.11.2026:** основа — один дискретный SimTick и явное игровое время. Целевая **пробная** длительность: **1 тик = 1 игровой час** (24 тика = сутки); для сравнения со старым симулятором оставить legacy-параметры 8 TPS / world_speed 0.25 отдельно. TPS (вычислительная частота) и игровая длительность тика — разные настройки. Частоту и масштаб календаря утвердить после короткой проверки реальных перелётов и циклов производства. Применение — **в P1, перед P2**, не откладывать до конца переноса. **Статус: решение записано, код нового календаря ещё не реализован.**

## Важное происхождение наших параметров

В исходном [Kalcode/spaceprojectsim `crates/sim_core/src/simulation/config.rs`](https://github.com/Kalcode/spaceprojectsim/blob/main/crates/sim_core/src/simulation/config.rs) есть `TickConfig::DEFAULT` со значениями **8 TPS**, `world_speed = 0.25`, `tick_scale = world_speed / TPS` и `tick_multiplier = round(TPS/world_speed)`. В нашем замороженном [Rust-эталоне](https://github.com/Mefits/Living-Sector/blob/archive/rust-galaxy-067-reference/native/crates/sim_core/src/simulation/config.rs) соответствующая часть совпадает по поведению. Следовательно, **эти числа унаследованы от исходного проекта; они не являются собственным обоснованным результатом сравнительных тестов Living Sector**. В [CLAUDE.md автора](https://github.com/Kalcode/spaceprojectsim/blob/main/CLAUDE.md) Rust-симулятор описан как перенос более раннего Elixir/Phoenix прототипа с Bevy-клиентом. Это происхождение не доказывает, что автор первым изобрёл тактирование.

## Как делают реальные студии

1. **Wube / Factorio.** Официальный [Factorio Wiki: Time](https://wiki.factorio.com/Time) определяет **60 UPS** как базовые игровые тики. В [Factorio Friday Facts #421, 26.07.2024](https://www.factorio.com/blog/post/fff-421) разработчики сохраняют единый tick, но выключают неактивные roboport, используют bucket updates и обновляют движущихся роботов не каждый шаг: следующий момент события рассчитывается заранее, а render-графика показывает промежуточную позицию. Для роботизированных тяжёлых сохранений приводят **10–25% улучшения всей симуляции** от этого конкретного подхода. Ключевое: **события и интервалы внутри тикового мира**, а не замена системы времени целиком.
2. **RimWorld / Ludeon.** [RimWorld Wiki: Time](https://www.rimworldwiki.com/wiki/Time) документирует 60 ticks/s и более редкие **250/2000** ticks. [Документация моддинг-библиотеки HugsLib](https://github.com/UnlimitedHugs/RimworldHugsLib/wiki/Custom-Tick-Scheduling) подробно показывает разнесение тяжёлых периодических пересчётов по разным шагам, чтобы избежать синхронного пика. Это данные community/modding, не инженерный diary Ludeon; не приписывать точную внутреннюю реализацию каждой подсистемы лично студии.
3. **Paradox / Victoria 3.** В официальном [Dev Diary #76 «Performance», 22.02.2023](https://www.paradoxinteractive.com/games/victoria-3/news/dev-diary-76-performance) технический руководитель сообщает: **1 tick = 6 игровых часов**, отдельно задачи по игровым дням/неделям/месяцам/годам. Tick tasks учитывают зависимости, возможны параллельные этапы и детерминированная сортировка; UI читает согласованные состояния между фазами, не посреди обновления бюджетов.
4. **Paradox / Stellaris.** [Stellaris 4.0 — 05.05.2025](https://www.paradoxinteractive.com/games/stellaris/news/stellaris-update-4-0): ради поздней производительности группы населения объединены, вместо расчёта множества отдельных pops. Это важно: **оптимизируют не только частоту, но и размерность модели**. Однако прямо переносить агрегированную логистику Stellaris нельзя: Living Sector требует настоящих кораблей и физических доставок.

## Что следует из сравнения

**Сохранить тиковое (дискретное) время как основу, не копируя произвольную частоту 8 TPS и полный обход всех сущностей при каждом шаге.**

Предпочтительная начальная архитектура:
- **Один `SimTick: int`** с последовательным порядком фаз. Он же надёжная опора для deterministic save/load и логов транзакций.
- **Периодические задачи с разной частотой:** локальные активные состояния — часто; производство/рынки/потребление/заработная плата/стратегия — по исходным игровым периодам, с распределением нагрузки по интервалу.
- **Планировщик событий по целевому тику:** известный момент доставки/окончания производства/контрактного дедлайна; events запускаются в правильной фазе и строго один раз. Изменение маршрута инвалидирует старое событие.
- **Визуальные позиции отдельно от тиков:** interpolation для CanvasItem/MultiMesh, не создавать фиктивную доставку на экране.
- **Синхронность денежных и физических операций:** при одновременных событиях порядок детерминирован и проверяется на одном и том же входе.
- **TPS, скорость ×16 и частота систем — сначала параметры**, а не окончательные законы. 8 TPS в PR #87 оставляем как baseline для сравнения с Rust, пока 100/1000/10000 агентов не дадут реальные измерения.
- **Не надо отдельного scheduler-фреймворка прямо сейчас.** Сначала один простой тик + распределённые интервалы, затем ограниченная очередь событий для действительно запланированных действий. Отделённый слой симуляции остаётся внутри Godot.

## Что делать с кодом PR #87

- Оставить `clock.gd` / `tick_runner.gd` как временный baseline, не выбрасывать без проверки.
- **Не переносить всю экономику как полную работу при каждом тикe**, но и **не переписывать её сразу в чистую event-driven**: особые события требуют взаимодействия с изменяемым миром, упорядочивания и сохранения.
- Начать со scheduler/cadence API и коротких тестов: детерминированность независимо от FPS; одинаковый итог ×1/×16 после одинакового числа игровых тиков; 1 платёж за контракт; save/load между двумя взаимозависимыми событиями; никаких `tick % 0`.
- Это **исследовательское решение без изменения процента подтверждённого порта**. Godot editor ещё не запускался. Статус P0=3/9, P1=0/9, итого 3/100 VERIFIED.
