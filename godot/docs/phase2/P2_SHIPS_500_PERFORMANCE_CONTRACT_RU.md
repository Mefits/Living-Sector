# Living Sector — 500 кораблей: ограничения на архитектуру и измерения

Дата: 17.11.2026. **Единственная рабочая ветка:** `feature/SystemBalance` («Баланс Системы»).
«Текущая» и «5 рабочих с Астрой» этим изменением не затронуты.

## Обязательное правило

Новая физическая навигация и кривые траектории должны быть спроектированы
для **не менее 500 одновременно существующих кораблей**, включая сотни
активных на одной карте, а не оптимизированы задним числом.
Нельзя подменять движение UI-анимацией, выключать реальную экономику,
пропускать списание топлива или прятать накопительное замедление
симуляции повышением FPS рендера.

**Проверять две независимые вещи:**

1. **Экран / FPS:** стоимость реальной отрисовки `StarSystemView`,
   получения отделённого UI-снимка и выбора корабля.
   Отдельные замеры на 50/500/1000 перемещающихся маркеров.
   Не отправлять весь N39/N9 World в карту каждый кадр.
2. **Симуляция / тики:** N14 упреждение, N140 LOD, новая проверка
   препятствий, N21 прибытие, N38 сохранения и их накопительная цена
   на продолжительном прогоне 500 настоящих кораблей.
   Синтетические маркеры не проверяют реальные N39/N9/ИИ расходы.

## Измеренное в настоящем Godot 4.7.2 (Linux GitHub Actions)

`godot/tests/p2_ship_scale_500_benchmark.gd`:
синтетические **визуальные** `transit.position` (не настоящие
порожденные N39 корабли); 24 обновления на каждый размер.
Замер `StarSystemView._draw()` внутри CanvasItem и CPU
`StarSystemView.set_live_fleet()`, не общий frame time.
Проходят реальные N14 `aim_point()` 500 раз для отдельной оценки.
Контроль асимптотики весьма мягкий: коэффициент 500/50
не должен превышать ×35; это **не** гарантия 60 FPS.

| Нагрузка | Исходно: draw mean | После упрощения: draw mean | Исходно: UI snapshot mean | После: UI snapshot mean |
|---|---:|---:|---:|---:|
| 50 | 1.065 ms | 0.655 ms | 0.596 ms | 0.418 ms |
| 500 | 5.299 ms | 2.997 ms | 5.259 ms | 3.736 ms |
| 1000 | 10.324 ms | 5.770 ms | 11.219 ms | 7.920 ms |

**Замеры — разные GitHub Actions VM-запуски, не строгий A/B
на одном и том же оборудовании.** Их нельзя интерпретировать как
доказанный процент ускорения, переносить на Windows FPS или
складывать с tick CPU без инструментального подтверждения.

- Исходный прогон: https://github.com/Mefits/Living-Sector/actions/runs/43961904330/job/133631201193
- Прогон после изменения: https://github.com/Mefits/Living-Sector/actions/runs/43962247768/job/133632434598
- 500 раз отдельный N14 solver: **23.452 ms в первом прогоне**,
  **15.043 ms во втором**, значительная вариация VM.
  *Это проблема возможных 500 solver-вычислений в одном
  живом тике; пока не доказано, что они вообще выполняются
  разом.* Никаких утверждений о полноценной 500-флотской
  симуляции на основании этих микробенчмарков.

В `StarSystemView` теперь копируются только два координатных
компонента `transit.position` вместо всех полей рейса,
а для удалённых кораблей рисуется одна точка без 12-сегментной
декоративной обводки. Выделение, клики по реальным кораблям,
сохранение и прогноз N14 остались прежними и прошли CI.

## Ограничения для физического облёта и дуг

- **Широкая фаза один раз по системам:** радиусы физических
  препятствий и их эпhemerides должны храниться индексированно;
  запрос корабля смотрит только кандидаты своего участка,
  а не все тела всех систем.
- **Маршрут по событию, а не по кадру:** сформировать путь при
  отправлении или при реальном изменении препятствия/цели.
  На каждом N14 fired тике двигаться к текущей точке курса;
  упреждение/облёт уточнять по ограниченной частоте,
  обоснованной точностью и динамикой, но без рассинхронизации.
  Потребуется детерминированное сохранение курсора в N39 и
  корректная повторная загрузка N38.
- **Стоимость на корабль:** ограниченное число препятствий и
  waypoint, верхняя граница итераций и воспроизводимый
  deterministic order. Нельзя вводить O(ships²), O(ships×all_bodies×
  every_substep) или покадровые 500 прогнозов.
- **LOD:** далёкие корабли могут отрисовываться простыми значками,
  траектории рисуются только для выбранных/приближенных объектов.
  Это *только графика*: существование корабля, топливо, товары,
  занятость маршрута, столкновения и экономика остаются в симуляции.
- **Нулевая дистанция/недостижимая цель/близкий облет:** не
  выдумывать бесплатное перемещение; при неудачном прогнозе
  сохранять безопасное состояние и реальные правила.
- **Профиль реальных 500 кораблей:** отдельно после объединения
  оптимизаций «5 рабочих с Астрой»; сценарий с 500 кораблями,
  50+ системами, скоростью ×16, не менее 10 000 тиков,
  динамикой времени тика по интервалам, p50/p95/p99, FPS
  и памятью. Длинный ночной Windows-тест может быть отдельным
  локальным сценарием, CI ограничить короткой проверкой.

Целевая планка UX — около 60 FPS камеры на тестовой Windows-машине,
но **пока это требование, а не достигнутый результат для 500 кораблей**.
