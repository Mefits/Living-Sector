# Living Sector / Godot P2 — план настоящей интеграции и протокол пяти смен

## РЕШЕНИЕ ПОЛЬЗОВАТЕЛЯ 13.11.2026 — АВТОНОМИЯ ПЕРВЕЕ РУЧНОГО УПРАВЛЕНИЯ

**Это главная текущая директива, выше старого порядка гейтов и списка UI-работ ниже.** Пользователь отменил приоритет индивидуальных приказов кораблям: ручную отправку/стыковку/передачу груза **законсервировать** (не удалять API и тесты), спрятать от игрока по умолчанию. Проект сейчас — автономный живой сектор в режиме наблюдения, а НЕ RTS с ручным управлением десятками кораблей.

**Новая цель ближайшей разработки:** без единого ручного клика в жизнь сектора вступают экономика → N135 администраторы станций/постановка заказов → N153/N80/N81/N84 решения кораблей → N104/N97 подтвержденные грузы/оплаченные контракты → N134/N100/N155 глава/Hybrid, реальные распоряжения и журнал причин/результатов. Сначала один полный автономный end-to-end цикл, потом расширять сценарии. Не внедрять вымышленные сценарные перемещения или фальшивые торговые операции, чтобы «корабли просто летали». Все действия проводятся через единственный N39 World, N9 Ledger, ContractBoard и Apply.

**Критерий успеха:** на чистом старте без ручного выбора корабля, назначения маршрута, контракта или строительства за N тиков есть реальные независимые решения и проверяемые изменения: агент обнаружил потребность → назначен заказ → выбран корабль → реальное перемещение и груз → доставка/списание/выплата; можно проследить цепь в наблюдателе, выполнить save/load и увидеть продолжение. Отдельно: администрация/фракция должна инициировать новые решения по живым данным, а не по фиксированным таймерам без нужд. Пока этого нет — **не называть проект автономным**. Отсутствие контрактов и бесконечный idle кораблей — явные блокеры, а не «нормальная готовность».

**Приоритет всем пяти сменам:** не делать UI кнопки ручной стыковки, маршрута или грузов, не выдумывать новых корабельных команд. Следующий свободный крупный блок брать по цепочке «автоматическая потребность → назначение → выполнение → receipt → наблюдение → save», начиная с N135/N153/ContractBoard, после проверки leases. Не откатывать существующее физическое ядро; оно понадобится автономным агентам. Прочитать [AUTONOMY_FIRST_RU.md](AUTONOMY_FIRST_RU.md).

Дата решения: 13.11.2026. Единая рабочая ветка `integration/godot-phase2-unified-20261113`, Draft PR #249.

## Зачем этот документ

Пользователь протестировал работающий Windows EXE: карта сектора, 8 систем, 3 фракции, 47 тел, реальное экономическое время. Сбой отсутствующей Galaxy data был исправлен в следующем Windows artifact [Actions #43403286156](https://github.com/Mefits/Living-Sector/actions/runs/43403286156). После него добавлен **исходный код** карты внутренней системы / инспектора тел, но сам новый интерфейс пока `CODE_UNVERIFIED` и **отсутствует** в старом artifact. Не путать source-only PR/успешный парсер с реально работающим поведением.

Главная цель: не писать очередные 100 source-only PR, а объединять все необходимые уже перенесённые Rust-механики в **один работающий и наблюдаемый симулятор**; обеспечить пользователю возможность проверять через Godot Editor локально без Actions после каждого коммита. Сначала работоспособные сквозные вертикали, потом полный паритет Rust 0.6.7. Не балансировать экономику заново без отдельного решения.

## Рабочий порядок и критерии готовности (не привязывать к сменам)

**Гейт 0 — надёжный локальный запуск для пользователя.**
- Довести новый sector → system → body → sector интерфейс до реального локального Godot запуска. Сохранить выбор, скорость, орбитальные углы, доступ к текущему World, не запускать второй TickRunner.
- Добавить ясную русскую инструкцию GitHub Desktop + Godot editor, при необходимости простой локальный cmd/PowerShell bootstrap (не бесконечную CI). Убрать вводящие в заблуждение подписи про неработающее потребление, если оно уже активно.
- Результат: пользователь сам нажимает Fetch/Pull и F5, может увидеть живые изменения; ошибок парсера нет.

**Гейт 1 — полный экономический цикл на одной модели.**
- Соединить N156 состояние/износ/ремонт, Crew/Welfare, N39 реальные производственные смены, N151 households, N150 market, кризисы где необходимо, НИКАКОГО второго ledger или двойного списания.
- Результат: материал, деньги, зарплата, население, ремонт и запасы меняются по одному тику; тест на сохранение равенства общего CR до/после транзакций. В интерфейсе видны реальные причины остановки производства.

**Гейт 2 — единая физическая модель флота.**
- Подключить исходные 24 корабля из того же Galaxy seed (без выдуманных ID), движение по **нативным** расстояниям/маршрутам, dock/undock, состояние, топливо, груз, экипаж и состояния корабля. N57 ship runner использовать как источник поведения, а не второй процесс/кошелёк/календарь. Учесть конфликты `ship_tick_runner.gd`, `ship_transit.gd`, `ship_state.gd`, `ship_catalog.gd`.
- Результат: хотя бы один реальный рейс стартует, проходит маршрут, прибывает, корректно занимает док и переживает save/reload. Показывать в GUI корабль, состояние, назначение, груз.

**Гейт 3 — контракты/торговля/доставка и единый Apply.**
- N97/N104/N152 ContractBoard/escrow, сделки на реальных рынках, склад → трюм → доставка → расчёт; один authoritative dispatcher и один N9 ledger, без фиктивных receipts. Учесть N35 контрактный runner и коллизию `contract_board.gd`.
- Результат: контракт может завершиться в реальном секторе; деньги/товары не создаются и не пропадают; контракт, груз и рейс восстанавливаются из checkpoint.

**Гейт 4 — поселения, строительство, технологии.**
- Реальная N151 миграция и N147 колонизация (после supply routes), N141/N154 стройка/shipyard и N143 исследования по материальным/временным требованиям. Для НОВЫХ объектов и ресурсов проверить стартовый seed, единственность ECS идентификаторов и непротиворечивость применённых команд.
- Результат: игрок наблюдает реальный проект/поставку/строительную смену/новый объект/исследование; все затраты подтверждены; save/reload не дублирует прогресс.

**Гейт 5 — глава фракции, администраторы, полноценные автономные решения.**
- N100 Hybrid Planner + N155 source domain/HTN/GOAP + N134 Director/mandates/персоналии должны видеть живую экономику и генерировать реальные ограниченные команды к одному Apply. «План готов» ≠ «действие выполнено». N150 отношения/территории, кризисы/пираты вводить только когда их effects можно исполнить.
- Результат: хотя бы одна фракция автономно обнаруживает потребность, выбирает действие, оплачивает/исполняет его и виден результат. Нужен наблюдаемый trace «причина → команда → результат».

**Гейт 6 — полный единый snapshot, долгосрочность, паритет и Windows-кандидат.**
- Собрать N157/SaveState для одного мира, денег, рынка, граждан, флота, грузов, контрактов, AI, строительства, исследований. Стабильная миграция схем либо явное объяснение несовместимых сейвов. Тесты 10/100/1000+ тиков (по нужде, не каждое изменение), save/reload, deterministic replay, контроль примеров против Frozen Rust 0.6.7.
- Финальная сборка Windows ZIP только после checkpoint, с **включённой** исходной папкой `data/galaxy`; убедиться что нужные экраны/состояния реально отображаются. Не заявлять полного Rust parity без проверки.

**Это зависимый backlog, не последовательные тикеты на одну смену.** Любая смена выбирает доступную полезную часть текущего самого раннего не закрытого гейта; если зависимости позволяют — можно параллельно подготовить следующий независимый блок. Если одну задачу не осилили, следующая смена продолжает её. Один реальный end-to-end результат лучше 10 guard/placeholder патчей.

## Жёсткая архитектура

1. Один `World` и один главный `TickRunner` (`godot/scripts/sim/phase2/n158_production_runtime.gd` до рефакторинга), одно игровое время и родная последовательность фаз из frozen Rust `engine.rs`.
2. Один `N9 Ledger`, реальные товарные запасы в едином world, один `ContractBoard`, один `SimCommand/Apply`, только один канал сохранения. Pure stage/propose adapter → validate → atomic commit; на failure нет тайного второго эффекта.
3. Не включать параллельно `production_tick_runner.gd`, `live_native_fleet_engine.gd`, `contract_tick_runner.gd` как независимые симуляции. Применять их логику внутри одной модели, с декомпозицией.
4. Не подменять frozen Rust 0.6.7 фантазиями: экономика/формулы/скорости/ресурсы/орбиты сохраняются; отдельные игровые решения, принятые пользователем, остаются неизменными.
5. Исполняющийся домен должен иметь: вход/выход реальных данных → один commit → наблюдаемый UI или debug inspector → roundtrip save/load → диагностику ошибок.
6. Устаревшие конфликты из `UNIFIED_IMPORT_CONFLICTS.json` разрешать в момент соответствующего домена, а не сливать всё автоматически.

## Протокол пяти смен — бесконфликтная общая очередь

- В каждом запуске прочитать `P2_INTEGRATION_EXECUTION_PLAN_RU.md`, свежий `UNIFIED_RUNTIME_STATUS_RU.md`, PR #249 HEAD, `P2_SHARED_HANDOFF_RU.md`, текущие leases и свежие коммиты. Не доверять stale claims/старым памяткам.
- Прежде чем менять файлы, проверить активные claims и взять небольшой атомарный lease на точные файлы/границы. 5 запусков сдвинуты всего на 5–10 минут и могут пересекаться по исполнению! Два исполнителя **не редактируют одновременно одни файлы**; при конфликте выбирать другой свободный участок или безопасную тематическую ветку, а не перезаписывать HEAD.
- Каждая смена автономно выбирает следующий наиболее ценный свободный участок по зависимости и результату предыдущих; **не назначать сменам постоянные номера/темы**. Разрешено продолжать незавершённое после проверки последнего коммита и освобождения/истечения lease.
- В каждом заходе реально писать/интегрировать игровой код. Избегать отчётов без изменений, микрокоммитов guard-only, бесконечного аудита, ненужных прогонов. Допустим крупный логически связанный участок и одна проверка.
- Handoff содержит: HEAD/коммиты, точный активный домен/незакрытый кусок, реально работающие методы, риск для единого ledger/clock, ошибки и узкое место, следующие свободные файлы, статус тестирования и схему rollback.
- Публиковать изменения в **один PR #249**, без новых десятков Draft PR; не force-push. Не трогать чужие выделенные файлы, не закрывать lease без результата.
- **GitHub Actions**: 0 запусков на мелкие коммиты, обычные PR или guard fixes. Сначала локальный Godot 4.7.2, доступный агенту, или статическая проверка с честным `CODE_UNVERIFIED`. 1 общий Actions smoke+Windows ZIP только после значительного сквозного завершённого гейта **или явного запроса пользователя**, если без него нельзя подтвердить сборку. Договориться об одном lease `CI_RELEASE_OWNER`; не обновлять файлы-маркеры параллельно; не пытаться rerun по старому SHA. Лог неуспеха разбирать ДО нового запуска.
- Не требовать от пользователя проверок во время его отсутствия. К вечеру подготовить краткий проверяемый отчёт со ссылками, гейтом и тем, что именно он сможет протестировать; если полноценный билд не проверен, так и написать.
