# Living Sector — Chat №1: реальные построенные врата и настройка пар (N108/N154/N38)

**14 ноября 2026 · PR #249 · `integration/godot-phase2-unified-20261113`**

**SOURCE_WIRED / CODE_UNVERIFIED.** Пользователь подтвердил: пока сохраняем транспортные врата между звёздными системами; T3/T4, необходимость врат и их окончательный баланс решаем позднее. Никакой новой технологии, бесплатной стартовой пары, правок экономики, запуска Godot или GitHub Actions.

## Результат

1. **Существующий платный N154/N141 стройцикл** при фактической материализации стройплощадки с `facility_type == "gate"` теперь переносит доказанный site.position и идентификатор N154 источника в единственный N39 World. Никаких материалов, персонала, капитала, сооружений или GateLink не добавляется сверх оригинальной оплаченной постройки. Пока нет реального построенного объекта, пары нет.
2. **NEW `unified_n108_gate_pair_stage.gd`**: явная установка взаимных `GateLink` из двух существующих активных `gate` в *разных системах*; проверяются реальность исходных тел, существующие позиции, отсутствие иной связи, парность, отсутствие повторного вызова. Поля равны frozen Rust `fee_flat=200, fee_per_cargo_unit=2, throughput_cap=3`. Создаётся отдельная append-only квитанция `native_gate_pair_receipts`. Нет автоматического выбора звёзд или доступа по технологическому уровню, нет переводов N9.
3. **N39 `apply_native_n108_gate_pair`** атомарно проверяет разрешённые два объекта и только их поля `gate_link/dirty`, неизменность всех денег/счетов, отсутствие новых сооружений/кораблей, прирост одной квитанции и Schema N39. Единственный World остаётся единственным источником данных.
4. **N158 `link_existing_native_gates(gate_a, gate_b)`** — явная точка интеграции оператора/администратора только при остановленной симуляции. Ввод не изменяет механики построек, решение игрока/фракции и T-уровни. Отдельный `N38` нормализатор сохраняет `native_gate_pair_receipts` и `GateLink.throughput_cap` после JSON.
5. **NEW `unified_n108_native_facility_orbit.gd`**: источник Rust `facility_offset_position(body_center, facility agent ID)`: `std::collections::hash_map::DefaultHasher::new` соответствует SipHash-1-3 ключ (0,0), в хэш Rust-строки включается UTF-8 + завершающий `0xff`. Угол берётся из беззнакового u64 % 360, радиус исходного Rust 0.55. Это **не** N43 FNV(location) и не произвольные координаты UI. В `native_location_resolver.gd::body_universe_position` берётся текущая оригинальная BodyOrbit, исходный смещённый центр и фактический угол.
6. **N108 фактический прыжок** теперь в едином N158 передаёт настоящий `WorldModel` в N39 source stage; координата выхода **на момент перехода** вычисляется из актуальной орбиты целевой планеты и Rust facility-id hash. Старая устойчивая позиция N154 site остаётся provenance для построенных врат, но не подменяет текущие орбитальные координаты выхода. Физический прыжок/плата по-прежнему происходят только через существующий `N84 → N146 → N158 → N39 → N108 P1 → N9`.
7. **Schema N39** принимает существующие необязательные pair receipts и проверяет exact 200/2/3; gate.position проверяется при наличии; унаследованные N151 colony dock/market/корабли не изменены.
8. **Отложенный файл проверки `godot/tests/p2_n108_native_gate_pair_check.gd`**: источник SipHash угол `hello→217`, built pair and current BodyOrbit, реальный N9 платеж (200+2×4=208), отказ для пустых/повторных/односистемных пар. **Код проверки добавлен, но не запускался**. Независимый BigInt расчёт для тестовых ASCII строк дал `hello=16156531084128653017 → 217°`, `facility-earth-gate-a→333°`, `facility-alpha-gate-b→11°`. Совпадение Godot будет подтверждено только при общем запуске.

## Осознанные ограничения и следующий шаг

- **Нет готовых врат** в восьми исходных стартовых системах; мы не добавляли их бесплатно. Родная Rust `strategy/construction.rs` не генерирует целевую цель `gate` из обычных дефицитов ресурсов; N154 *исполнитель* материально оплаченного объекта типа gate теперь готов, но полностью автономный выбор построить врата не реализован. **Это намеренно — пользователь отложил техуровни и стратегическую роль врат.**
- Явная пара работает на двух существующих построенных и оплаченных вратах; отсутствует UI выбора пары и автоматическая выдача этой команды игровым фракциям. Это не ошибка транспорта, а ещё не принятое правило доступности. После интеграции можно добавить инструмент игрока с выбираемыми двумя ID.
- Оригинальный N4 навигационный граф из seed не превращаем в фиктивные межзвёздные обычные `Travel`-линии. `GateJump` уже сохранён как отдельный тип BT-действия и реальный физический `RequestGateJump`. Остались отдельные AI-источники маршрутов исследования и назначения mining-goal.
- **Не проверено:** GDScript parser, Godot runtime, F5, реальные построенные ворота через N141, N38 full restore, Rust/Godot hash parity в живом движке, игровой маршрут между системами. Результат статической проверки 8 GDScript файлов: строки/скобки/инденты/EOF/методы связаны; GitHub Actions 0. Полный прогон откладываем до завершения переноса по инструкции пользователя.
- Соседние чаты работают над колонизацией, фракционным ИИ и финальной сборкой. Chat1 не менял баланс и не перезаписывал чужую работу; все shared-file записи с актуальным SHA.
