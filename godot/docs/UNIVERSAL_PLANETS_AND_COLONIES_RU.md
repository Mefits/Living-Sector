# Единая визуализация планет и колоний — SystemBalance

## Что реализовано

Все видимые тела используют **один** `star_system_view.gd`, одну
детерминированную `planet_surface_projection.gd` и одну
`physical_assets_projection.gd`. Нет отдельного рендера на каждую планету.

- Внешность берётся из `system.id`, `body.id`, `body.biome` и
  опционального `body.surface_seed`. Континенты, кратеры/озеро, точки
  предприятий и центр связей воспроизводимы после загрузки.
- Опциональный `physical_radius_km` либо `radius_km` задаёт
  пропорциональный схематичный размер планеты. Если данных нет, используется
  существующая категория типа тела. Известные диаметры Sol остаются
  эталонным запасным вариантом, а не отдельной картой.
- Луна любой системы с `parent_body_id` и
  `satellite_orbit_radius_native` рисуется на орбите родителя;
  `current_angle` / `orbit_period` остаются в общей механике.
  Для замороженного Sol действует прежний проверяемый адаптер
  `native_satellite_orbit_profiles.gd`; неизвестные орбиты не
  придумываются.
- Исходные `world.facilities` и **новые** `N39.facilities` объединяются
  только в read-only проекции. Динамический объект показывается, только
  если у него есть подлинные `body_id`, `type` и `location`, а
  `body_id` принадлежит текущей системе. Нет бесплатных построек.
- N151: новая `construction_dock` по адресу `<body_id>-colony`
  видна как строящийся центр; когда **тот же** `facility_id` приобретает
  тип `station`, его символ превращается в административный центр.
  Координата привязана к ID: по окончании строительства здание не скачет.
- Таблицы колонии, карточки, инспектор и правый аутлайнер читают те же
  живые N39-факты и видят вновь созданный объект. Клик выбирает реальный
  facility ID.
- Дороги — только визуальные связи между известными предприятиями на
  **одной планете**, активность — по оплаченной N39 смене. Группировка
  по планете и месту вместо общего квадратичного перебора.

## Схема для будущей процедурной генерации

Пример минимального тела (это **контракт данных**, не новая сущность N39):

```json
{
  "id": "planet-273",
  "type": "planet",
  "biome": "terrestrial",
  "surface_seed": 273102,
  "physical_radius_km": 4800,
  "orbit_radius": 4.8,
  "orbit_period": 1100,
  "current_angle": 135
}
```

Спутник дополнительно задаёт `parent_body_id` и
`satellite_orbit_radius_native` в единицах мира.
Случайный генератор может создавать тысячи таких записей, не создавая
GDScript-файлы на каждый объект. Обязательна уникальность ID в WorldModel.

## Что НЕ делает этот этап

- Не создаёт физические миры, новые навигационные узлы, население или
  ресурсы. Генератор **галактики как симуляционных данных** и сохранение
  новых систем в WorldModel/N39 требуют отдельного изменения источника
  истины: сейчас существующая навигация N151 использует зарегистрированные
  исходные тела.
- Не меняет N43/N14 физическую орбиту или платное строительство N39.
  Вне Sol орбитальные станции без явных координат имеют **неподвижный
  схематичный маркер**, а не выдуманное орбитальное движение.
- Не задаёт настоящих географических координат наземных сооружений.
  Site — воспроизводимое символическое место на поверхности; физические
  грузовые доставки следует подключать отдельно.
- Не гарантирует визуальную приёмку: Godot в среде редактирования не
  запускался. Проверки:
  `godot/tests/p2_universal_planet_colony_visual_check.gd`,
  `p2_sol_physical_assets_check.gd`,
  `p2_system_balance_colony_roads_check.gd`,
  `p2_sol_moon_closeup_lod_check.gd`.

## Граница производительности

Профиль поверхности собирается на загрузке системы или изменении
списка исходных тел. Новые N39-объекты перестраивают только
представление предприятий при изменении набора/type/body/location,
а не на каждом кадровом рендере. Дорожные связи ограничены по каждой
планете и не соединяют разные системы/тела.
