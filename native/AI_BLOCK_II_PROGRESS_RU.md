# Блок II — многозвенное автономное планирование: исходники подготовлены

**База:** итоговый архив Block I от 10.11.2026. **Состояние:** Rust-код изменён, компиляция и испытания намеренно отложены. Без сборки нельзя считать этот блок работающим в Galaxy.

## Внесённые изменения

1. **Единый нативный каталог для нескольких станций.** Вместо одного производителя на конечной станции включены доступные нативные рецепты каждой принадлежащей фракции станции с *одним однозначно принадлежащим рынком*. Продукты промежуточного рецепта можно доставить к следующей фабрике в той же области планирования. Включены лишь релевантные цели действия; обратное замыкание по выходам, входам и местам назначения не ограничено заданным рецептом или именем теста. Для головной цели всё ещё используется +10 единиц, штатный бюджет 350 узлов и глубина 12 — они не увеличены без игровых измерений.
2. **Многозвенные цепочки на существующих рецептах** (`Ore -> Metals -> Components -> Electronics`, `Ice -> Water -> Food`, `Gas -> Polymers -> Components` — возможные пути, а не подтверждённые прогоны). Никаких виртуальных запасов: поисковый переход потребляет реальные входы в своей *прогнозной* модели, производит все выходы рецепта и расходует прогнозные деньги за доставку.
3. **Поставщики и партии.** Выбор из нескольких собственных однозначных складов, разные размеры доставок (потребность рецепта, до 10, до 20 единиц), возможность прогнозировать производство недостающего товара у удалённого поставщика *до* отправки. Прогнозные максимум три смены только задают размер предполагаемой партии; все входы каждой смены обязаны покрываться переходами поиска. Неправильная явно указанная цена исключает маршрут.
4. **Ранее принятые обязательства.** Обещанный груз по `posted`/`accepted` контрактам вычитается из *прогнозного* доступного запаса источника (не затрагивая ECS и оплаченные реальные контракты). Новые действия доставки не конкурируют за такую же комбинацию товар/получатель, если уже есть активный контракт. Предполагаемые источники с несколькими рынками по-прежнему заблокированы, а исходный рынок проверяется по устойчивому ID.
5. **Корабли — дефицитный ресурс.** На начальном снимке считаются только свободные корабли в каждой точке, исключены назначенные на действующие обязательства; один корабль даёт не более одного стартового исходящего рейса в символической цепочке. Это не маршрутизация корабля: возвращение/перестановку нужно моделировать отдельно. Проверка грузоподъёмности, топлива, маршрута и кошелька повторяется нативным исполнителем.
6. **Причины ожидания.** Для HTN различаются `no_plan`, `budget_exhausted`, `invalid_snapshot`; глубинный предел не выдаёт ложный вывод о невозможности цели. Гибрид аналогично возвращает отдельные диагностические причины. Предыдущий механизм отложенных целей и backoff сохранён; новые контракты из прогнозов сами по себе не создаются.

## Что НЕ делалось

- Никаких `cargo check/test/build`, запуска Genesis, API, игровых сценариев, сравнений алгоритмов, кросс-компиляции или коммитов Git.
- Не изменялись `Cargo.toml`/`Cargo.lock`, игровой баланс, рецепты Genesis, производство, население, схема SQLite, Observer и стратегия главы.
- Не вводились альтернативные искусственные склады/валюта/производство; исполнение — только через прежние native receipts и контрактный механизм.

## Ограничения и риски для финального этапа

- HTN/GOAP/Beam получили больше возможных действий, но при нынешнем жёстком бюджете сложная цель может закончиться `budget_exhausted` — это **не** доказательство отсутствия решения.
- Прогноз не знает полную стоимость экипажей, индивидуальные деньги корабля, реальную проходимость маршрута, прибыльность переработки и скорость производства; исполнитель обязан перепроверять эти условия. Непройденный нативный шаг вызывает ожидание/перепланирование, а не фиктивный успех.
- Маршрут между станциями включается, только если у источника *изначально* есть свободный перевозчик. Действий для возвращения или перевода кораблей в другую систему этот блок не добавляет.
- Продукт, который другие процессы успели потребить между шагами, не резервируется сам по себе. Перед каждым действием мир перепроверяется. Добавление явного резерва партий и перевозчиков потребует отдельного контракта исполнительного уровня.
- Действующий контракт на тот же товар в тот же пункт назначения сохраняется, даже если он задержан; такой товар исключён из нового каталога перевозок до завершения/отмены старого обязательства. Это сознательно консервативное поведение.
- Существующие потенциальные ошибки компиляции блока I также наследуются: этот исходный пакет не проверяет их.

## Отложенные проверки при заключительной интеграции

1. Компиляция полной накопленной базы I+II+III+IV; при сбое устранить именно ошибки изменённых модулей.
2. Глубокая цепочка с производством на станции A, доставкой на B и последующим производством на B; каждый шаг подтверждён real receipts.
3. Две альтернативы поставщика на одном снимке: выбор без двойного списания или телепортации грузов.
4. Одно- и двухкорабельный вариант: символический поиск не использует один корабль для двух одновременных исходящих отправок.
5. Уже оформленный контракт: оплаченный escrow и груз не дублируются при переключении плана/рестарте.
6. Источник с двумя рынками на одной позиции: никакого объединения чужих запасов.
7. Исчерпан бюджет vs нет доступного сырья: разные reason_code и возврат к нативной политике.
8. Финальное сравнение baseline, HTN, Telic/GOAP, Beam и гибрида на одной и той же сохранённой Galaxy.
