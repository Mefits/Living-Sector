Решение пользователя: реализовать функциональность крупными блоками, отложив Cargo, unit-тесты, игровые прогоны и оценку стабильности до заключительного интеграционного этапа. ## 1. Производство и реальные квитанции (перенесено из WIP)

`crates/sim_core/src/strategy/planning/native_execution.rs`:

- Накопительный выпуск фиксируется для **каждого выходного товара** нативного рецепта отдельно (`action_id::output:<commodity>`).
- Для `process_ice` два фактических выхода, вода и топливо, признаются без двойного зачёта; повторные оплаченные производственные смены учитываются отдельно.
- Завершение плана определяется фактическим выпуском запрошенного товара, включая побочный.
- Приоритет нативного администратора учитывает побочный продукт шага, если это товар цели.
- Чтение старых checkpoint-полей оставлено только для соответствующего первичного продукта; недостающие фактические квитанции нельзя заменять прогнозом.

## 2. Финансирование и контракты (добавлено при закрытии блока I)

**Единственная формула для обоих контуров.** `sim_core/economy/contracts.rs` предоставляет `acceptance_payment()` и `funding_top_up()`. `sim_server/engine/contract_funding.rs` использует их при окончательном принятии, сохраняя реальную проверку payer ECS и атомарное списание только после успешного захвата контракта. Старое правило запрета несанкционированной доплаты к фиксированной награде оставлено.

**Выбор на актуальном снимке.** `sim_core/agents/ship/behavior.rs` один раз за цикл кораблей снимает доступные балансы плательщиков по **типу funding** (faction/facility/population), затем каждый корабль проверяет собственную quote с его comms и treaty. Кандидат с нехваткой средств/некорректным escrow отфильтровывается **до** выбора лучшего предложения. Другие допустимые публичные контракты и обычные задачи остаются кандидатами. В apply-фазе защита повторяется против живого мира: предфильтр не гарантирует платеж при конкурентном списании.

**Отказы.** Отрицательный receipt `ShipTransaction::Accept` запоминается по (ship, contract_id) с причиной и версией существенных условий (status/payment/funding/reserved/payer balance/quote). При неизменной версии действует ограниченный retry backoff; пополнение или изменение цены/escrow делает запись неактуальной. История ограничена 32 записями на корабль. Уже существующий серверный `ship_transaction_rejected` сохраняет реальную причину отклонения; отдельно не добавляли новый шумный event на каждый отфильтрованный контракт.

**Перезапуск.** Список последних отказов сохраняется в существующий `ShipResumeState.resume_json` вместе с текущим экономическим кадром. Новое поле снабжено `serde(default)`, старые сохранения без него должны загружаться без миграции БД. Обычные контракты/escrow продолжают сохраняться их собственным нативным путём.

**Станционные назначения.** `sim_core/strategy/orders.rs` не назначает корабль на фиксированно оплачиваемый заказ с недостаточным/повреждённым резервом, выставляет `blocked_reason=invalid_order_escrow` и освобождает назначение. Когда резерв исправлен, заказ можно снова назначить без ожидания старого cooldown. Не меняются договорённости о физической доставке или сроках заказа.

- Только нативный исполнитель меняет деньги, грузы, производство и обязательства; теневые планы не являются фактами.
- Никаких новых ресурсов, балансов ИИ и бесплатных escrow; прежние `contract_funding` и `ReleaseContract` остаются источниками истины.
- Данные Galaxy, рецепт, стоимость построек, стартовые корабли, параметры личности и игровой баланс не менялись.
- Не обновлены зависимости/lockfile, не пересобраны поставленные бинарники, ничего не отправлено в Git.
