# Observer 0.1 — первый пользовательский осмотр (2026-11-04)

**Источник:** скриншот работающего Windows Observer; отзыв владельца Living Sector. **Статус:** подтверждённые UX-проблемы и предложения, НЕ согласованная новая спецификация.

## Замечания владельца

1. «Пока вообще не понятно что с этим делать». Нет главного действия, назначения режима, понятного фокуса и дальнейшей цели.
2. «Сейчас работает всё и сразу, поэтому не понятно с чего начать». Симуляция запускается без вводного этапа; сразу видны 6 систем, ~282 корабля, ~93 станции и десятки рынков. Следует продумать осмысленный вход в наблюдение, паузу при запуске Observer, выбор одного объекта/процесса вместо всех сразу.
3. Изначально предполагалось движение по линиям в духе Stellaris, но жёсткое ограничение «только по линиям» нежелательно. Разделить граф навигации и визуализацию, сохранить свободу дальнейших механик передвижения.

## Что видно на скриншоте

- Скопление разноцветных обозначений кораблей непосредственно над системами мешает читать масштаб сектора.
- Пустой инспектор постоянно занимает примерно пятую часть экрана.
- Лог показывает внутренние ключи событий и JSON (например, SHIP DOCKED), а не понятную историю.
- События происходят до того, как пользователь выбрал предмет наблюдения.
- Карта передаёт топологию, но не помогает отличить транспорт, экономические проблемы и важные действия.

## Сверка с кодом — НЕ выдумывать новый транспортный закон

- `crates/sim_core/src/world/pathfinder.rs`: `WorldRegistry.routes` — обычные `Travel`-рёбра между локальными точками; `gate_pairs` — межсистемные `Gate`-рёбра. Реальные пути планируются через Dijkstra.
- `crates/sim_core/src/agents/ship/actions.rs`: `GateJump` мгновенный, обычный `Travel` занимает время и расходует топливо; в снапшоте корабля есть `transit.from/to`.
- `crates/sim_core/src/agents/ship/mod.rs`: **при недоступности пути найден fallback к прямому Travel**, а исполнитель действий при отсутствии `travel_distance` использует дистанцию 60. Следовательно, утверждение, что в текущей симуляции межсистемное движение строго ограничено вратами, было бы неверным. Этот fallback требует осознанного решения — это либо экстренный запасной механизм, либо потенциальный обход планирования и платы за врата. Не менять без отдельного теста и согласования.

## Предлагаемый следующий интерфейс (НЕ реализовано)

1. Старт Observer: явно объяснить назначение, выбрать режим / начальный фокус, остановить время перед знакомством с миром. Пауза при старте **только через launcher Observer**, чтобы не менять поведение всех headless-клиентов.
2. На масштабе сектора: системы, связи существующих врат, активность и потоки на основании реальных данных. Не рисовать сотни отдельных кораблей при общем масштабе по умолчанию.
3. На масштабе системы: корабли, станции, реальные перемещения и состояние хозяйства; фильтры по действиям из `current_goal` и `current_bt`, не выдуманные типы.
4. По клику: компактный инспектор с фактическими задачами, грузом, рынком, связанными действиями. Пока объект не выбран — не резервировать большую пустую панель.
5. Журнал: перевести известные event types на понятный язык, опускать технический JSON; хранить доступ к сырым данным через отдельное Debug.
6. Сети: отображать врата как **существующую транспортную инфраструктуру**, а не автоматически превращать линии в физические рельсы. Будущие режимы свободных прыжков / двигателей — только после разработки механики и её цены для экономики.

**Приоритет:** сперва наблюдаемость и UX, не добавление новых судов/войн/конвоев. Поведение ядра не менять из-за визуального пожелания без доказательного теста.
