# Living Sector — блок C: гибрид Utility + HTN + GOAP + Beam

**Статус:** исходники подготовлены поверх **непроверенного компиляцией блока B**. Тесты Rust и реальное исполнение новой версии **ещё не подтверждены**. Не заявлять «готовая гибридная галактика» до результатов `VERIFY-AI-BLOCK-BC.cmd` и реального сценария перевозки.

## Что теперь соединено

1. **Utility и личности Genesis** остаются в `strategy/coordination.rs` / `strategy/director.rs`. Они выбирают важную **игровую цель** (снабжение, исследование, экспансия). Никакой второй таблицы черт характера не создано.
2. **HTN 0.2.1** предлагает декомпозицию локальной товарной задачи на последовательность реальных действий (`Deliver` / `Produce`).
3. **Telic 0.1.0 + точный GOAP-поиск** получает *подзадачу по входящему товару* для одновходовой финальной производственной операции HTN. Если он находит путь, система составляет единый проверяемый план `GOAP снабжение → HTN производство`. Из того же ограниченного бюджета GOAP дополнительно проверяет **прямую альтернативу** всей цели (например, готовая вода вместо переработки льда). При сложной структуре HTN, которую пока нельзя безопасно разделить, GOAP решает полную цель как альтернативу.
4. **Beam Search** с ограниченным бюджетом вызывается **избирательно**: когда валидные пути расходятся или HTN+GOAP не нашли исполнимого решения.
5. **Оценка кандидатов** принимает предпочтения существующего командира: экономический вес, срочность, осторожность. Профиль влияет на выбор **между разрешёнными** планами; не делает недопустимую перевозку допустимой.
6. **Реальное исполнение** — ровно существующий `NativeExecution` блока A: нативная доска контрактов, гарантия оплаты, реальные корабли, квитанции производства и сохранение с директором. Не создаются ресурсы или деньги из прогнозов. Старые HTN-планы в сохранениях продолжаются без миграции.

Для проверки: `crates/sim_core/src/strategy/planning/hybrid.rs`, `native_catalogue.rs`, `native_execution.rs`, `coordination.rs`.

## Безопасность и ограничения

- По умолчанию всё как было: `LIVING_SECTOR_PLANNER` не задан → работает обычный Genesis.
- Старый режим `LIVING_SECTOR_PLANNER=htn` не меняет алгоритм (только поля отчёта расширены совместимым образом).
- **Новый режим `LIVING_SECTOR_PLANNER=hybrid`** должен выбираться пользователем явно; отделён от штатного сохранения при запуске тестового CMD.
- Все планировщики видят один `PlanningSnapshot`, один каталог `ActionSpec`, одну казну и один набор прогнозных остатков. Никаких независимых «виртуальных» складов/банков.
- `validate_plan` + повторное последовательное применение всех нативных количественных эффектов (`safe_candidate`) для каждого предлагаемого плана. Исполнитель повторно проверяет **живое** ECS и контракты до любого реального расхода.
- Единый ограниченный бюджет **350 узлов для всего гибридного поиска**, а не 350 на каждый алгоритм; распределяется 40/40/20 % между HTN / GOAP / опциональным Beam. При проверке ингредиента GOAP делит собственную долю между подцелью и полной альтернативой. Лимит глубины 12.
- Один активный план/фракцию; шаги, квитанции и связанные контракты сохраняются. `NativePlan.planner_rationale` имеет serde-default для старых сохранений.
- Новый отчёт содержит `planner_id`, `planner_rationale` и mode `native_hybrid_opt_in`; ради обратной совместимости API поле головы пока называется `htn_execution` — оно несёт отчёт как HTN, так и hybrid.
- GOAP не обязан уступать HTN при разных прогнозных расходах; если совместная цепочка эквивалентна HTN, при равенстве предпочитается именно **кооперация** HTN+GOAP.

## Чего блок C пока НЕ умеет

- Не строит через HTN произвольную цепь технологий T1–T4 и не командует военными флотами.
- Нативный исполнитель сейчас умеет **контракты перевозок и наблюдение за реальной производственной сменой**, но не создаёт через гибрид напрямую заводы, исследования или колонии. Для них остаётся существующий директор Genesis.
- Периодически невозможно получить однозначные рынки, свободные корабли или полную цепочку: корректный результат — fallback на Genesis с причиной. Это не доказательство «плохого» планировщика.
- У Beam нет гарантии нахождения лучшего пути. Не запускать все алгоритмы постоянно.
- Отложено детальное сравнение автономных кампаний с одинаковым RNG/временем и устойчивая верификация на 100 системах.
- Даже после успешной компиляции короткий запуск API докажет только запуск **нового** бинарника, а не успешную реальную доставку по гибридному плану. Для этого нужен отдельный контролируемый runtime-сценарий с подтверждённой оплатой/прибытием и сравнением с baseline.

## Одна проверка B+C на Windows

Из корня проекта запустить **`VERIFY-AI-BLOCK-BC.cmd`**. Это **один** пакет, объединяющий:

- Cargo check `sim_core` + `sim_server` + `sim_db` (первый запуск разрешает `telic = 0.1.0` в lockfile);
- короткие unit-тесты планирования, координации и администраторов;
- сборку нового `genesis_server.exe`;
- два фиксированных чистых сравнительных примера B и C по `tests/ai_block_b_fixture.json`;
- короткую проверку, что **новый** Windows-сервер с `LIVING_SECTOR_PLANNER=hybrid` открывает `/api/health` и `/api/strategy` на **отдельной временной базе**. Стратегическое событие может не наступить за время smoke — это честно только API-проверка.

Все логи и `Cargo.lock` упакуются в **`AI-BLOCK-BC-RESULTS.zip`**. При ошибке не нужно запускать тесты многократно: передать архив с ошибкой. На рабочую БД Galaxy эти проверки не пишут.

После успешных проверок ручной экспериментальный запуск (при необходимости): `RUN-HYBRID-BLOCK-C.cmd` — отдельная БД, порт 18081, Observer. Не объединять результаты с исходным сохранением.

## Следующий крупный этап после B+C

Один *реальный контролируемый* сценарий Genesis: вода отсутствует в колонии → лёд добыт в другом месте → HTN разбивает задачу → GOAP выбирает доставку → нативный контракт принят/оплачен/довезён → refinery выполняет реальный оплаченный выпуск → ИИ видит квитанцию и сохраняет прогресс после рестарта. Измерить затраты и число неудачных приказов, сравнить со старым Genesis и одиночным HTN. **Не расширять баланс T1–T4 до доказательства этой цепочки.**
