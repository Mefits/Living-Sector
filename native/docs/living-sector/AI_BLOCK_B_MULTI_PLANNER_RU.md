# Блок B — GOAP/Telic + Beam поверх реального Genesis

**Статус:** исходники подготовлены. **Cargo и Rust недоступны** в рабочей среде автора блока. Прохождение `cargo check`, `cargo test` и работа в новом EXE **не подтверждены** до получения результата от пользователя.

## Принцип

Рабочий директор Galaxy 0.2 и включаемое исполнение HTN блока A сохранены без изменения. Новый код ничего не списывает, не строит, не телепортирует. Три альтернативы **на одном и том же** `PlanningSnapshot`, `GoalSpec`, `Vec<ActionSpec>`:

- `HtnAdapter` — существующий HTN 0.2.1 (возможно включить нативное исполнение блока A отдельно).
- `TelicGoapAdapter` — настоящая `telic 0.1.0` строит символические GOAP-подсказки, затем **глобальный bounded best-first** перепроверяет каждый шаг на точных запасах, расходах и кредите. Это честно **Telic-guided exact search**, а не чистый Telic GOAP, способный самостоятельно учитывать количества; адаптер так и назван.
- `ControlBeamAdapter` — **bounded width=16** Beam без Telic-подсказок, но на тех же точных состояниях и действиях.

Все три используют `htn_adapter::domain_from_native`: проектор не суммирует два рынка в одной локации, не производит товар без рецепта/доступного производства, не тратит один склад дважды и не позволяет расходовать неприкосновенную казну. Эти **прогнозные** ограничения не проверяют реальный маршрут, расходы топлива, зарплату и Native Execution — перед исполнением по-прежнему нужны живые проверки.

### Границы честного сравнения

`compare_planners()` сравнивает алгоритмы на **одном входе**, логирует статус, шаги, узлы поиска, прогноз кредитов/тиков и результат общего `validate_plan()`.

- По одному снимку **нельзя определить, какой ИИ развивает фракцию лучше**: для этого нужны одинаковые сохраняемые игры и метрики после реального исполнения.
- Текущий Genesis baseline выбирает первый административный шаг с другим горизонтом; его **нельзя честно оценить той же метрикой краткосрочной водной цели**. В отчёте он отражён как действующий директор, но не маскируется четвёртым эквивалентным планировщиком.
- Телисовская модель Boolean GOAP может пропускать реальные ресурсные ограничения; её предложения не считаются исполнимыми до перепроверки точного состояния.
- Производство в планах — только прогноз. Успех шага в игре подтверждает нативная квитанция и действительные изменения ECS.
- Ограничены `max_nodes`, `max_depth`; `budget_exhausted` не доказывает невозможность цели.

## Как увидеть результат

В текущей Galaxy по умолчанию ничего не меняется. **Только в новом собранном бинарнике** и при явном включении:

```cmd
set LIVING_SECTOR_PLANNER_SHADOW=1
set LIVING_SECTOR_PLANNER_COMPARE=1
```

В `/api/strategy` → `head.planning_shadow.planner_comparison` появится разбор одного снимка. Блок A опционально запускается через `LIVING_SECTOR_PLANNER=htn` (исполнение **только HTN**, GOAP и Beam не посылают заказы).

Для запуска чистого сравнения **без сервера, без обращения к сети и без изменения БД**:

```cmd
cargo run --locked -p sim_core --example compare_ai_native -- tests\ai_block_b_fixture.json
```

Один скрипт проверки для пользователя — `VERIFY-AI-BLOCK-B.cmd`. Он проверит Cargo, целевые тесты, соберёт Windows сервер, выполнит сравнение на JSON-снимке и соберёт `AI-BLOCK-B-RESULTS.zip`. Без этой проверки **не объявлять новый блок рабочим**.

## Что не сделано

- Не переключается native dispatch на GOAP или Beam: это задача гибридного блока C после runtime-проверки блока A.
- Нет гарантии переносимости прогнозов между рестартами: только нативный план/квитанции блока A сохраняются.
- Никакого нового T1–T4, экономики и отдельного симулятора.
- Нет ещё сравнения кампаний на фиксированном горизонте тиков, нет доказанного лидера среди HTN/GOAP/Beam.

## Короткая приёмка

1. `cargo check` — все `sim_core`, `sim_db`, `sim_server` проходят.
2. Тесты `strategy::planning` — HTN, общая модель, GOAP, Beam и безопасное сравнение проходят.
3. Тестовый JSON даёт три валидных плана «доставить лёд → переработать → вода» без создания льда из ничего; при нулевом льде нет ни одного ложного Ready.
4. Чистое сравнение детерминировано; `LIVING_SECTOR_PLANNER_COMPARE` по умолчанию выключен, не влияет на расход денег/заказы.
5. Runtime-проверка после сборки: отдельно новый EXE, новая БД, несколько циклов, проверить появление сравнения и отсутствие неожиданных грантов/контрактов. **В этом пакете она ещё не выполнена.**

**Следующий блок C:** архитектурная гибридизация Utility/Personality → HTN этапы → Telic GOAP подзадачи → выборочный Beam при альтернативных путях, с ограничением бюджета и управлением Native Execution. Комбинация должна доказать полезность на реальных, а не только символических задачах.
