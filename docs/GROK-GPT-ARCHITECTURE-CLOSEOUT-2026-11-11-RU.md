### Нюанс сенсоров

Поле называется sensor_range_au, значения T1=1.0, T2=2.0, T3=3.5. В логике межзвёздных заказов это просто порог: в той же системе — доступно, в другой системе — нужна величина не ниже 2.0. Физическое расстояние между звёздами в а.е. при этой проверке НЕ рассчитывается. Название неточно; механику модулей не перерабатываем сейчас.

## Последовательность этапов, каждый отдельным PR

### S2. Выяснить реальный блокер доставки
Целевой инструмент: ограниченный test-only inventory для ship + contract, показывающий действительные reasons: видимость репутации, допуск по отношениям, сенсоры, существование маршрута, source stock, capacity, source purchase cost, payment quote, escrow top-up, planner selected goal, accept or reject. Никогда не объявлять причину по корреляции общих отказов. Отделить законный дефицит межзвёздных перевозчиков от настоящего дефекта. Только после установления причины — один точечный regression и маленькая правка. Не менять модульные T1/T2 и не создавать новые валюты/ресурсы.

### Golden-v1. Нативная экономическая цепочка
На test-only controllable seed (отдельная копия, а не production SQLite) создать давление food/water/gas с настоящим источником и достаточным свободным кораблём. Наблюдать pressure → AI goal → authorized native contract → accepted → picked_up → delivered units → verified causal stock relief. Разделять delivery_verified, relief_verified, resilience_verified. Paid, Posted или увеличение stock без causal attribution не являются успехом. Три НЕЗАВИСИМЫЕ fresh-DB прогона только после одного короткого green-probe. Отдельный вариант без свободного перевозчика должен показывать blocked, а не fake success.

### Source 0.6.3. Устранить двойной источник истины
Версия 0.6.3 проверена в CI, но пока собирается из overlay scripts, тогда как прямое дерево исходников в Git относится к 0.6.2. Получить полный source snapshot именно зелёного 0.6.3 и import в ОТДЕЛЬНУЮ ветку. Проверить direct-source Windows compile + smoke без overlays, затем совместимость прежнего SQLite на КОПИИ (load → 100–300 ticks → save → restart). Только после этого отказаться от старого пути сборки, сохраняя старый snapshot для rollback. Не сливать в стабильную ветку без этих gates.

### Player Agency и resilience
Отдельным PR: один реальный выбор игрока в уже существующих mandate/charter (направление supply/research), ограниченный native казной. Не раздавать приказы отдельным кораблям, не создавать ресурсы из воздуха. Делегирование и hold должны изменять решения главы и показывать причины в Observer; life-support overrides остаются.
Затем повторные кризисы, проверка recovery/resilience и сохранений. Итог — stable snapshot + передача документации и подтверждённых тестов другой модели.

## Планеты — отдельная будущая идея, НЕ implementation сейчас

Предложение: сделать поверхность планет полноценной экономической площадкой с населением, складами, фермами, шахтами, фабриками и управлением; станции остаются орбитальными логистическими/специализированными узлами.

Перспективный архитектурный принцип: экономика работает с общей абстракцией экономического узла (owner, location, market, storage, production), а тип узла (планета / станция) задаёт физические ограничения, транспорт до орбиты и специализацию. Это может позволить переиспользовать native производство и администраторов без второго симулятора.

Но простое копирование станционной системы на планеты уничтожит роль станций и создаст вопросы поверхности↔орбиты, стройки, перевозки и сохранений. На данном этапе только концепт, без кодовых изменений, PR и расширения текущего Golden-теста. Обсуждать после закрытия перечисленных архитектурных этапов.
