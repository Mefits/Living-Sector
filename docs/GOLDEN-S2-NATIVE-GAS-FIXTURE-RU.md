# Golden S2 — контролируемая проверка настоящей доставки газа

**Версия:** direct-source native Galaxy 0.6.2 + отдельные патчи сенсоров/диспетчера из PR #64/#67/#68.

**Тест/исходники:** PR #69, `ci/sol_s2/prepare_fixture.py`, `ci/sol_s2/assess_fixture.py`, CI workflow `native-062-s2-gas-golden-fixture.yml`. Запуск https://github.com/Mefits/Living-Sector/actions/runs/43026028736 .

## Зачем нужен тест

Старый S1 обнаружил реальное накопление дефицита газа на Earth Station, хотя были размещены и оплачены заявки Alpha → Earth. После исправления сенсоров единственный Huge Hauler получил T2, однако успел принять другой контракт и находился в физическом перелёте до тика ~1970, за пределами прошлого наблюдения. PR #68 добавил подхват *уже оплаченных*, но никем не принятых заказов предприятия своим свободным перевозчиком без обхода обычных ограничений.

Нужна настоящая цепочка: `shortage -> native facility prepaid delivery contract -> station order/ship planner -> Accept -> Buy -> Travel -> Deliver -> contract_delivered market receipt`, а не только зелёные юнит-тесты.

## Честные ограничения контрольного опыта

Именно в `work/s2-game` создаётся временная копия всех оригинальных JSON; `native/priv/galaxy/data` и стабильная игра не изменяются. Отличия:

- В Earth gas supply = 0, demand gas = 8 (сразу есть pressure).
- В Alpha gas supply = 6000, test-only gas unit price = 1.5.
- Существующая двусторонняя магистраль Earth–Alpha вместо 120 получает расстояние 6. Все другие рёбра, восемь систем и настоящие механизмы передвижения остаются.
- Huge Genesis Hauler стартует на Alpha с конечными 950 кредитами, обычными `comms_t2`, обычными по размеру сенсорами T2; модульные эффекты игры не изменяются.

Это намеренно делает *возможный рейс* короче, но не создаёт никаких товаров в процессе доставки, не выдаёт ИИ бесплатных денег и не меняет логику торговли. **Положительный исход не доказывает устойчивость экономики на настоящих 120 единицах дистанции.**

## Что считается проверенным

- Результат `delivery_verified=True` только если в настоящем `/ws` имеется `contract_delivered` на точный `contract_id`, газ, Earth Station и native `Delivery` с реальным `FundingSource::Facility` и escrow; объём подтверждён из того же контракта. Фактический event пишется после нативного увеличения market supply (исходник `engine/apply.rs`).
- `relief_verified=True` только если после такого receipt дополнительно замечено положительное количество газа на рынке Earth и последующее уменьшение счётчика `shortage_ticks`. Отсутствие таких наблюдений не подменяется догадкой.
- `resilience_verified=not_tested` — повторные кризисы здесь не моделируем.
- `Posted`, `Accepted`, расход/резерв денег, движение корабля и даже `Paid` **не являются доказательством доставки** без нативного события.
- На красном gate сохраняются исходные `samples.jsonl`, `events.jsonl`, `genesis-server.log`, `manifest.json` и диагностика, чтобы искать конкретный блокер, а не строить теории по общим счётчикам.

## Что должно быть после теста

1. Если `delivery_verified=True`: проверить связку `ship_transaction_applied/accept,buy,deliver` по тем же ship_id/contract_id, затем провести обычный world-distance тест и отдельный food/water Golden.
2. Если `delivery_verified=False`: выяснить по реальным JSONL — были ли создана оплаченная gas заявка, кому назначили, что помешало Buy/Deliver, и почему долго сохранялся shortage. Не повышать скорость, не ослаблять sensor T1/T2, не создавать фракционные деньги и не считать Goldens пройденными.
3. Результаты держать в экспериментальной ветке; не переносить в `main` или стабильную сборку до окончания приёмки.

**Примечание о provenance:** старый pinned `ci/sol_s0/probe.py` выводит исторический `build_source_sha` базовой версии. Настоящим SHA тестовой сборки считать **head_sha GitHub Actions run 43026028736** и опубликованный хеш `genesis_server.exe` в workflow log. Историческое поле в probe manifest не равно этому SHA.
