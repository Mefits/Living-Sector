# A2 — приказы администраторов станции

Ветка: `feature/genesis-station-orders`, поверх A1 `97d6d63430a772e78ccf252b211c6db9c8078cc0`.
PR #43. Код `990eafc08219099fd0b9223f5f046d551f40cb53` прошёл CI 42404470189. Финансы остаются
отложены; используются уже существующие бюджеты, сделки, escrow и зарплата.

## Рабочая цепочка

1. A1 наблюдает все модули `(faction_id, location)`, назначает местный персонал и
   формирует нехватку производственных входов. Эти Need добавляются в портфель
   логистических целей главы; одинаковые товар/станция не дублируются.
2. Глава по прежней системе сравнивает доставку, строительство и ожидание.
   Сам запрос не заставляет главу покупать: при отсутствии прогнозируемой пользы
   существующая оценка спроса/цены выбирает ожидание.
   Станция не получает отдельный кошелёк или право обходить разрешение главы.
   Уже существующий контракт своей фракции на тот же товар/станцию блокирует дубль.
3. `strategy/orders.rs::dispatch` перед параллельным проходом кораблей последовательно
   распределяет профинансированные стратегические перевозки и готовые к труду стройки.
   Только корабли той же фракции; один исполнитель на приказ и один приказ на корабль.
4. Перевозчики сравниваются по низкому топливу, длине доступного маршрута и стабильному
   ID; проверяются свободный трюм, текущая занятость, физический запас, цена покупки,
   деньги корабля и торговые отношения. Строитель должен иметь инженерную роль.
   Уже принятый контракт и сохранённое назначение имеют приоритет над новым заданием.
5. Корабль строит штатный BT. Назначение перевозки не зависит от публичного порога
   репутации. Заправка и отдых остаются вариантами при выборе начала задания.
   Native Accept/Buy/Deliver повторно проверяют фактические условия и проводят сделки.
   Попытка принять чужое назначение или второй контракт отвергается до списаний.
6. Строитель летит/стыкуется штатно; труд начинается только при реальном присутствии
   назначенного корабля на активном Construct. Оплата и рабочие смены остаются F3/F4.
7. Пропавший исполнитель, конкурирующее обязательство или тайм-аут освобождают
   назначение. Повторное назначение увеличивает attempt, сохраняя order_id. Пауза
   перед повтором — 30 базовых тиков; ожидание принятия/прогресса — 300, с tick multiplier.
   Принятую перевозку освобождает только native release/expiry/settlement, не таймер A2.
8. После загрузки исполнители восстанавливаются по стабильным ID. Груз и деньги
   читаются только из native компонентов; сохранение приказа само ничего не оплачивает.

## Сохранение и API

`Order` находится рядом с долговечным обязательством: `ContractFunding.station_order`
в существующем `funding_json` и `ConstructionLabor.station_order` в `labor_state`.
Оба поля необязательны при чтении старых сохранений. Новых таблиц и миграций нет.
ContractBoard сохраняется целиком в economic frame, изменённая стройка отмечается dirty.
JSON содержит только управление, не дополнительную сумму денег/материалов.

`/api/strategy.orders[]` (добавление к прежнему v1):

| Поле | Значение |
| --- | --- |
| order_id | `station:delivery:<contract_id>` / `station:construction:<site_id>` |
| faction_id, location | Ключ станции |
| kind, target_id | delivery/contract или construction/site |
| commodity | Товар перевозки; null для строительного труда |
| quantity, completed_quantity | Товар либо рабочие смены; единицы зависят от kind |
| executor_id | Стабильный ID корабля либо null |
| state | waiting, assigned, executing, blocked, completed, cancelled |
| blocked_reason | Наблюдаемая причина отказа/ожидания, либо null |
| attempt, assigned_tick, retry_after_tick | Номер назначения, время назначения и следующей попытки |

Связь с `stations[].needs[]` — по faction_id/location/commodity. Need сам по себе
не означает, что глава уже одобрил расход. `assigned` не означает физическое прибытие.
`executing` перевозки выводится из принятого контракта, стройки — из оплаченной смены.
Результат перевозки подтверждается Paid. Завершённая стройка превращается в native
Facility и исчезает из списка текущих приказов; отдельный архив приказов не вводится.

## Ограничения для A3

- A2 выбирает маршрут по прямым связям WorldRegistry (или той же локации).
  Полная межзвёздная диспетчеризация через граф ворот остаётся A3.
- Цена/сырьё не резервируются диспетчером. Конкурирующая покупка может лишить приказ
  выполнимости; native транзакция откажет, затем происходит пересмотр.
- Потребность входа пока использует прежнюю партию SUBSIDY_QUANTITY и стоимость
  логистической политики главы. Это не расчёт точного производственного заказа.
- Не меняются независимые коммерческие контракты. Уже принятые независимым кораблём
  стратегические контракты до введения A2 продолжаются без захвата управления.
  Пока нет назначения, фракционный корабль сохраняет обычные варианты деятельности.
- Добывающие модули управляются через персонал A1. Нового действия добычи кораблём
  и физической миграции населения A2 не добавляет. Нельзя объявлять их готовыми.
- Управление персоналом сервисов/доков, частичная работа предприятий, адаптивные
  размеры заказов и многосистемная координация остаются незавершёнными.
- Новый приказ планируется до начала перевозки. Уже принятое обязательство не
  бросается ради более выгодной торговли; топливо обрабатывает штатный BT.
- Shadow не создаёт новых назначений. Уже записанные обязательства сохраняются.
- Тайм-аут стройки относится к отсутствию оплаченного прогресса, включая отсутствие
  людей/бюджета, а не автоматически к вине корабля; причина доступна в labor.

## Границы передачи

Не менять параллельно `strategy.rs`, `strategy/orders*`, `agents/ship/behavior.rs`,
`agents/construction*`, `economy/contracts.rs`, server `engine.rs`, `contract_funding.rs`,
`snapshot.rs` и общий workflow. Это граница ядра A2. Observer/карта/камера не менялись:
их разработчик может использовать добавленный orders API, неизвестные поля — «—».
Никакие открытые PR автоматически не объединяются. Следующая модель продолжает
проверенный SHA этой ветки, а не подвижную интеграционную ветку другого чата.

## Адресные проверки

- Два одновременных заказа получают разных исполнителей; исчезнувший корабль
  заменяется после паузы с тем же order_id и увеличением attempt; деньги не меняются.
- Shadow не назначает, недостаток средств/трюма виден, тайм-аут допускает повтор.
- Стройка и перевозка делят один набор кораблей, назначение сохраняется в JSON.
- Планировщик видит свой приказ без публичной репутации и сохраняет выбор заправки.
- Сервер проводит настоящие Accept/Buy/Deliver: чужой исполнитель отвергается,
  Paid подтверждён, груз доставлен и общая сумма денег сохранена.
- Настоящий SQLite roundtrip сохраняет приказ контракта; checkpoint стройки
  восстанавливает назначенного строителя, труд и затем материализует объект один раз.
- 7 проверок A1 остаются зелёными. Первый прогон остановился на отсутствующем Debug
  у нового API DTO; исправлено до прошедшего прогона.
- Добавлена адресная проверка Need → глава → контракт без повторного списания;
  её итог будет закреплён финальным SHA.

Длительный автономный прогон с полётом между станциями не запускался. Проверки
подтверждают составные исполнительные пути и сохранение, а не баланс большой галактики.
Релизные/Windows-сборки не запускались.
