## Что действительно работает и что проверено

- Глава сравнивает предложения логистики и строительства до списания денег.
- Логистика выбирает выполнимую потребность; строительство продолжает свою площадку
  или выбирает производителя для хронического дефицита.
- Один новый оплаченный стратегический контракт на фракцию за цикл; старые контракты
  могут исполняться одновременно. Источник оплаты — реальная казна, native escrow.
- Покупка/доставка, материализация объекта и перевод капитала проверены адресно.
- [CI S4](https://github.com/Mefits/Living-Sector/actions/runs/42198362786): 27 разных
  тестов (30 запусков из-за пересечения фильтров), genesis_server build, fresh-world API smoke.

**Не подтверждено:** полный стратегический цикл с самостоятельным выбором контракта,
реальным перелётом и стыковкой, длительное развитие обеих фракций, полный цикл после
перезапуска. В native-интеграционных тестах перелёты заменены перемещением fixture;
строительный тест завершает уже частично готовую площадку. Не называть это доказанной
автономной стройкой с нуля. Windows-сборка с объединённым актуальным Observer не готовилась.
Проценты готовности из беседы — субъективная оценка, не критерий приёмки.

## Архитектурные решения, которые сохранять

| Решение | Где смотреть / почему |
|---|---|
| Исходный Rust/Bevy ECS + SQLite остаётся ядром | `sim_core`, `sim_db`, `sim_server`; не заменять их Genesis Clean или вторым симулятором |
| Предложение отделено от исполнения | `strategy/coordination.rs`: сначала оба администратора в shadow, затем grant одному; списывает native путь |
| Один источник экономической истины | FactionData, ContractBoard, funding/escrow; head.spending_limit — расчёт, не кошелёк и не ReservationBook |
| Подтверждённые транзакции исполнителя | `sim_server/src/engine/transactions.rs`; сохранять проверки груза, цены, владельца, стыковки, доступности и однократности |
| Состояние проекта выводится из native объектов | persisted markers strategy.logistics.v1 / strategy.construction.v1; площадки и контракты переживают загрузку, решения/портфель — transient |
| Согласованный checkpoint | `engine/persist.rs`, `engine/drains.rs`, `sim_db/src/persistence.rs`: EconomicFrame, удержание при backpressure, retry после ошибки, creation до tombstone |
| Стройка не получает бесплатный капитал | Перевод из казны до 20000; стабильные отрицательные DB-id построек, origin площадки в миграции 016 |
| Observer только читает | `/api/strategy` schema_version=1; новые поля добавлять совместимо, старые не переименовывать |

Runtime вызывает coordinator из `agents/faction.rs` каждые 60 * tick_multiplier тиков.
Не подключать новых администраторов независимыми списаниями в соседнем участке tick:
их предложения должны участвовать в выборе главы. Прямые вызовы существующих
администраторов в тестах проверяют отдельные слои, но не заменяют production pipeline.

Политика S4 пока фиксированная: выполнимое снабжение Food/Water/Fuel → начатая стройка →
новое производство → обычная логистика. Score и стабильный tie-break действуют внутри
уровня. Это прототип, а не утверждённый окончательный баланс. Резервировать все будущие
этапы стройки для диагностического режима не требуется.

## Границы прототипа — не скрывать за новыми методами ИИ

- Стройка пока потребляет доставляемый дефицитный товар по старой модели 600 единиц;
  нет полноценной ведомости материалов и отдельного корабля-строителя.
- Товар у источника не резервируется при планировании; Buy проверяет реальный stock.
- Выбор producer соответствует рецепту/добыче, но будущие входы рецепта и прибыль
  не гарантированы. Автоматического планирования всей производственной цепочки нет.
- Нет полного replay RNG/BT/crew, durable истории решений и полного world checkpoint.
- `head` — последний выбор и бюджет; старые status/selected_goal фракции — логистика;
  `construction` — отдельное решение/площадка. `projects[]` содержит поставки:
  paid одной поставки не означает готовность здания; null site_id не доказывает завершение.
- Shadow не замораживает экономику: стратегический слой не тратит, legacy-процессы работают.

## Ближайший блок S5: автономное исполнение, 6 связанных задач

1. На отдельной свежей БД воспроизвести ограниченный по тикам сценарий с реальными
   кораблями, источником товара, топливом, целевым дефицитом и достаточной казной.
   Зафиксировать начальные условия; не менять мир вручную после старта.
2. Проследить глава → администратор → posted → самостоятельный Accept → Buy →
   реальные вылет/полёт/стыковка → Deliver/Paid. Не телепортировать исполнителя.
3. Исправить только фактические блокеры этой цепочки; при таймауте сохранять причину,
   цель, контракт, положение/топливо/груз исполнителя и состояние источника.
4. Довести стройку от нулевого прогресса до объекта несколькими реальными поставками;
   проверить расход материалов, капитал и отсутствие дублирования после завершения.
5. На копии БД/контрольной точке проверить перезапуск с удерживаемым контрактом:
   продолжение работы без повторной оплаты, покупки полного уже загруженного груза
   или создания второй площадки. Не объявлять это полным детерминированным replay.
6. Записать результаты отдельно для обычной и пиратской фракций: что подтверждено,
   что заблокировано и почему. Затем переходить к оценке альтернатив/последствий
   и реакции главы на неудачи, сохраняя общий путь исполнения.

Успех S5 — наблюдаемый результат без тестовой подмены движения, с ограниченным временем
проверки и коротким воспроизводимым отчётом. Если текущий мир не даёт такого результата,
не подменять успех искусственной доставкой и не расширять работу до общего аудита экономики.

## Работа и совместимость

Основной разработчик владеет strategy/ECS/tick pipeline/SQLite/экономическими инвариантами.
Второй разработчик — Observer, визуализация и независимая диагностика; точные файлы,
схема API и конфликты: [PARALLEL_DEVELOPMENT.md](PARALLEL_DEVELOPMENT.md).
Общие STATUS/ASTRA/HANDOFF обновляет владелец ядра; UI ведёт OBSERVER_STRATEGY_NOTES.md.

Один функциональный блок из 5–10 задач — одна ветка/PR, промежуточные коммиты допустимы.
Адресные тесты по изменению, интеграционная проверка на контрольной точке; не запускать
полный suite и не повторять аудит без причины. Некритичные проблемы — в backlog.
Для нового ответвления явно включить нужный сценарий в CI: текущий workflow перечисляет
ветки, сам по себе новый branch name не гарантирует запуск проверок.

Сейвы проверять на копии/новой БД. Миграции только вперёд и совместимо со старыми строками;
старый бинарник не направлять на уже обновлённую БД. Не удалять оригиналы сохранений.
Запуск: DATA_DIR=priv/genesis/data, отдельный DATABASE_PATH,
LIVING_SECTOR_STRATEGY_MODE=execute; `cargo run --locked -p sim_server --bin genesis_server`.
По умолчанию shadow. Параметры HTTP/скорости и изоляции — в `tests/strategy-runtime-smoke.py`.
