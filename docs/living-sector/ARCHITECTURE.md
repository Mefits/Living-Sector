# ARCHITECTURE — адаптация The Space Project

**Дата статического обзора:** 2026-11-03. **Основа:** `Kalcode/spaceprojectsim` @ `967b9b6`. **Проверка компиляцией/запуском:** НЕ выполнена в рамках этого переноса.

## Реальная структура upstream

- `crates/sim_core` — экономическая и агентная логика Rust: корабли, рынки, объекты, население, фракции, AI, командный буфер, граф путей.
- `crates/sim_db` — SQLite, загрузчик, миграции, сохранение.
- `crates/sim_server` — headless runner, HTTP/WebSocket API, снапшоты, управление.
- `crates/client_bevy` — графический Bevy-клиент, 3D-сцена, egui-интерфейс, локальный цикл симуляции.
- `crates/sim_protocol` — типы сообщений.
- `priv/data/worlds/*.json`, `priv/data/factions.json` — исходные данные мира.
- Исходный [docs/ARCHITECTURE.md](../../ARCHITECTURE.md), [CLAUDE.md](../../CLAUDE.md) — полезны, но иногда устарели относительно текущих Rust-файлов.

Исходный проект уже содержит production/consumption, рынки, транспорты, контракты, базовую фракционную политику, `FactionRelations`, `BodyTerritory`, `AgentStore.system_control`, а также отображение цветных подписей объектов. Визуальная мини-карта ещё не равна большой политической карте в духе Stellaris.

## Рекомендуемое направление изменений

```text
       существующая симуляция (Rust / bevy_ecs)
                         |
        -----------------+-----------------
        |                |                |
   новые модели       сохранения       проверка мира
   знаний/экспедиций  и история         и replay
        |                |                |
        +----------------+----------------+
                         |
          стабильная проекция состояния
                         |
        +----------------+----------------+
        |                                 |
   стратегическая карта              отложенный
   Bevy + egui                       личный режим
```

Сохранить **один источник истины** для экономики, владения, складов, кораблей и событий. Новые фракционные знания должны быть отдельным состоянием от истинного состояния объектов. UI только отображает состояние и отправляет контролируемые команды.

Для карты использовать существующие координаты `WorldRegistry.systems` и отношения/владение из симуляции. Расчёт цветных зон — **производный слой визуализации** (не подменяет экономическое владение): спорные/нейтральные системы должны корректно отличаться. Позже можно добавить масштабирование, разные режимы и исторические срезы.

## Что уже обнаружено как технический риск

1. **Разные циклы выполнения.** `client_bevy/src/sim/mod.rs::tick_sim` и headless `sim_server` считают мир разными путями. Комментарии описывают отложенные async/persistence пути; нельзя считать их эквивалентными без тестов.
2. **Сохранение оконного режима.** По коду клиент загружает SQLite, но не вызывает полный рабочий цикл фоновой записи, в отличие от server. `Save As` использует SQLite copy. Требуется проверить реальное сохранение изменений и исправить расхождения прежде, чем положиться на сейвы.
3. **Детерминизм не доказан.** Наличие `world_seed` само по себе не гарантирует одинаковый outcome для агентов. Для A/B-вселенных нужны versioned RNG, стабильный порядок обработки и тесты.
4. **Ряд исходных комментариев устарел.** Некоторые файлы уже используют `bevy_ecs`, но документы упоминают `hecs`, а старые комментарии называют этапы, выполненные позже.
5. **История не полноценный replay.** Есть журналы событий/команд, но нужно отдельно определить долговременные причинные записи, снапшоты и механизм воспроизведения.

Всё выше — **статические наблюдения**, а не результаты запуска. Никаких утверждений «проект сломан» без воспроизводимого сценария.

## Инварианты, которые надо проверить/ввести

- Сохранение/загрузка: запуск 100 шагов и запуск 50+сохранение+50 дают одинаковое состояние.
- Два режима запуска: одинаковые initial state, tick count и команды → одинаковые существенные состояния (или объяснимый documented delta до исправления).
- Товары и кредиты изменяются только при явном производстве/потреблении/обмене/потере.
- Два конкурента не могут без механики конфликта одновременно получить один уникальный объект.
- Историческое событие содержит идентификаторы причин, объектов, временные метки.
- У отложенной экспедиции есть источник знания, расходы ресурсов, отправление и прибытие.
- Никакие локальные визуальные эффекты не должны менять экономическое состояние мира сами по себе.

## Техническая стратегия

**Не переписывать `sim_core` на C# или GDScript.** Предварительное исследование до выбора upstream рассматривало отдельное C# ядро, но теперь эта рекомендация устарела. Сохраняем Rust/Bevy, пока не появятся измеренные причины делать иначе.

Добавлять расширения максимально модульно и подключать к явным фазам тика; соблюдать текущий `SimCommand` для изменений других сущностей. Не обещать автоматическую совместимость с будущими upstream-изменениями; она зависит от затронутых файлов и тестов.

Интеграция будущего режима персонажа должна разделять глобальное и локальное состояние. Внимание: наличие `InGameView::Interior` в текущем клиенте — только заготовка переключения режима, **не работающий персонаж**.
