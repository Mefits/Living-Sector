## Product design document / техническое ТЗ для Codex

**Редакция:** 2026-11-04 · **Статус:** рабочая целевая спецификация.  
**Проект:** [Mefits/Living-Sector](https://github.com/Mefits/Living-Sector) — fork Kalcode/spaceprojectsim, Rust / Bevy ECS / SQLite / headless HTTP + WebSocket / Observer (HTML Canvas).  
**Рабочая ветка существующего Genesis:** `feature/genesis-0-1`, черновой PR #4 поверх `feature/observer-focused-ui` (PR #3, который сам зависит от PR #2). Не сливать PR в неправильном порядке.

> **Цель документа:** дать Codex понятную задачу с границами и критериями завершения. Отделять согласованную продуктовую цель от того, что **уже есть** в репозитории, от временных решений и открытых инженерных вопросов. Не принимать пример данных или ранний Observer за готовый Genesis.

## 1. Концепция / почему это интересная игра

**Living Sector — автономная космическая экономика, которую интересно наблюдать потому, что у её событий видны причины.** Игрок — наблюдатель: видит, как небольшая фракция самостоятельно организует добычу, транспорт, промышленность, снабжение, расширение, а позже конкурирует за ресурсы и территории. Мы используем существующее ядро The Space Project, но строим собственный стратегический 2D-интерфейс.

Успешный момент Genesis 0.1: **первый новый корабль** появился не по таймеру и не административным spawn, а потому что фракция выявила логистическую потребность, выделила бюджет, физически получила необходимые материалы, верфь завершила корпус и комплектацию, и корабль стал новым постоянным действующим агентом. После рестарта он существует вместе со всеми последствиями расхода ресурсов.

**Антицель:** случайные значки и новости без причин, сотни кораблей с первого кадра, бесконечные бесплатные товары, «производство» в UI без работы двигателя, красивый макет вместо работающей симуляции.

### 1.1 Принятые продуктовые принципы

1. **Малый старт:** 1 звёздная система, 1 фракция, от 1 до 5 настоящих кораблей; по умолчанию 3. Есть маленькая база с ограниченной инфраструктурой и энергией.
2. **Всё имеет происхождение:** добыча → перевозка → переработка → компоненты → строительство / обслуживание / снабжение. Запасы физически привязаны к месту; между разными местами нет телепортации.
3. **Нет бесплатных пополнений:** новые корпуса, грузы, объекты и энергия требуют явно описанного источника и затрат; никакой автозамены списанных кораблей в Genesis.
4. **Локальная энергия:** стартовая станция даёт минимальную мощность, её можно расширять генераторами (ранний пример — солнечные). Потребители конкурируют за доступную мощность; недостаток должен замедлять/останавливать часть работы.
5. **Несколько видов сырья:** разные составы, добыча и переработка, не все залежи доступны/известны без разведки и оборудования. Каждая стартовая система имеет базовые ресурсы для развития; более ценные/редкие — повод к экспансии.
6. **Самостоятельные фракции:** глава выбирает общие стратегические приоритеты; администраторы промышленности, снабжения, строительства и позже экспансии готовят проекты; исполнители действуют в рамках реальных ограничений.
7. **Объяснимость:** по каждому значимому решению можно ответить «кто, зачем, на каком основании, где деньги и материалы, почему не получается, когда результат».
8. **Постоянство:** события и состояния переживают рестарт, а интерфейс отображает авторитетные данные Rust/SQLite.
9. **Простота дизайна:** новый объект, специализация или формула только если создаёт наблюдаемую причинную цепочку; не усложнять экономику ради количества механик.
10. **В будущем** несколько систем, независимые компании, конкурирующие фракции, картография 100/250/500 св. лет и даже персонаж — **не условие завершения Genesis 0.1**.

## 2. Что сейчас реально есть, а чего нет

| Подсистема | Текущий статус в этой ветке | Что требуется до завершения 0.1 |
|---|---|---|
| Genesis seed | `priv/genesis/data/`: 1 Sol, 1 Genesis Initiative, 3 корабля (2 freighter + courier), 4 тела, 6 facilities, 2 рынка | Проверить игровой баланс, сделать минимальную реально работоспособную экономику, не путать seed с финальной версией |
| Запуск | `Start-Genesis.cmd`, `DATA_DIR`, отдельный `genesis.db`, headless, Observer в браузере | Проверить повторный запуск/пауза/сохранение/новая БД, не ломать обычный `sim.db` |
| Корабли | Реальные ECS-агенты и маршруты/контракты. Observer получает `transit`, `location`, `docked`, `system_id` | Устойчивые рейсы, реальные поставки, устойчивый малый флот, производимый новый корпус |
| Добыча | Существующий `mining_rig` добывает один агрегат `Ore` из ресурсов тела | Явные местные источники/остатки, минимум 2 осмысленные разновидности руды; корабельная добыча только если даёт ценность первой вертикали |
| Производство | Existing `recipes`, refinery/factory, рынок-склад в `MarketPricing.supply`, module production на верфи | Проверенная цепочка от добытого сырья до производства корпуса/модулей без двойного учёта и магических запасов |
| Верфи | Могут производить **модули**, но не новые корпуса | Заказ и постройка корпуса за материалы, энергию, время, бюджет с созданием реального агента |
| Ресурсы/энергия | Нет полноценной локальной сети мощности | Генераторы, потребители, баланс и последствия дефицита |
| Фракции | Есть финансы, отношения и отдельные процессы, но нет согласованного иерархического planner для Genesis | Стратегическая цель → проверяемые проекты администраторов → бюджет/резервы → реальные действия |
| Обновление флота | Существующий механизм бесплатных `PendingRespawn` | Отключить **для Genesis**, не удаляя механизм из старого стресс-мирa |
| Observer | Живые `/api/report`, `/api/health`, `/ws`, выбор объектов, карта, пауза/скорость. UI развивается | Контекстные экраны и причинные цепочки вместо большого технического списка |

**Не выдавать таблицу «в будущем» за сделанное.** Исходные компоненты могли измениться: Codex должен проверить актуальный код и скорректировать технические привязки.

## 3. Сценарий первого запуска

**Фиксированные границы испытания:** 1 Sol, 1 фракция, 3 корабля, ограниченная стартовая денежная масса, 2 раздельных хозяйственных района (база и ресурсный узел) с маршрутом, реальные доступные ресурсы, малый источник мощности. Числа баланса (производительность, цены, стоимость корпуса) — конфигурируемые, не захардкоженные в UI.

**Стартовый состав:** пока seed содержит 2 грузовика и 1 курьер, а добывает стационарная установка. Это **промежуточное техническое состояние**, не повод выдавать его за майнер-ИИ. После появления подходящей механики допускается один корабль-добытчик вместо одного грузовика, если это не срывает вертикальный цикл.

**Целевая наблюдаемая история без скриптов:**

1. Фракция видит, что существующие 3 корабля и база ограничивают снабжение/производство.
2. Администратор промышленности находит недостаток сырья/компонентов, другой — проблему логистики или мощности.
3. Добывающий узел извлекает именно тот материал, который реально есть в месторождении; местный склад растёт, месторождение истощается либо расходует проверяемый доступный объём.
4. Перевозчик физически проходит между двумя точками, транспортирует груз (с момента отправки он не доступен в исходном складе, до прибытия — в пункте назначения).
5. Перерабатывающий объект расходует входные материалы + выделенную энергию и создаёт выходные продукты после технологического времени.
6. Промышленность получает комплектующие; верфь получает проект «Новый грузовой корабль», бюджет/материалы резервируются.
7. Верфь выполняет заказ не мгновенно, расходует материалы и энергию, выпускает **корпус с минимальным рабочим комплектом**. Новый корабль появляется в доступной точке верфи, получает постоянные ID и принадлежность фракции.
8. Он участвует в следующем логистическом задании; в отчёте видно, какую проблему решило добавление.
9. Рестарт: новый корабль, остатки/заказы, планы и изменения мира сохраняются без удвоения.

Если какой-либо шаг заблокирован, это не «случайный простой»: показать реальную причину (нет денег, нет материалов, нет питания, нет свободного транспорта, неизвестна технология, верфь занята) и доступный следующий проект.

## 4. Системы и правила

### 4.1 Месторождения и знания

- У источника имеются ID, тело/положение, состав (по типам сырья), доступная/общая ёмкость, пригодность добычи, возможно условия/сложность. Не генерировать бесконечный товар `Ore` в `MarketFlow.production`.
- Минимальный набор для 0.1 — **не менее двух различающихся видов полезного сырья** с разными цепями переработки или требованиями оборудования. Конкретные товарные ID подобрать в ревизии `Commodity`, не вводить несовместимые магические алиасы.
- Для первой системы критические базовые ресурсы доступны. Неопознанные/сложные залежи могут требовать разведки/оборудования; фракция не должна знать их без источника информации.
- Добыча уменьшает измеримый источник, увеличивает склад; регенерацию существующего `BodyResources` в Genesis проверить и не оставлять незаметной бесконечной подпитки. Если необходима регенерация, она должна быть явным игровым законом, а не «безусловной пачкой товаров».
- Не надо на первом этапе придумывать геологию галактики, десятки минералов и исследования длительностью годы.

### 4.2 Запасы, транспорт, производство

- У каждого логистического места/объекта определён **единственный авторитетный** складской источник. Текущий `MarketPricing.supply` может быть отправной точкой, но не дублировать его отдельным `Warehouse` без ясной синхронизации.
- Для каждого товара сохраняется бухгалтерский инвариант: `начальный остаток + добыто/произведено/импортировано − потрачено/потреблено/утрачено − вывезено = текущий остаток` (с отдельным учётом груза в пути).
- У перевозки есть источник, пункт назначения, корабль, вид/количество груза, основание/заказ, состояние, фактическое отправление/прибытие, возможная ошибка. Проверять вместимость, запас, доступность маршрута.
- Производство расходует входной ресурс и производит выходной **однократно**; недостаток любого компонента блокирует/ограничивает запуск. Никаких «появилось на складе назначения без судна».
- Сохранение и загрузка не должны повторять торговую операцию, двойное списание, создание заказа, создание корабля.

### 4.3 Энергия и эксплуатация

- Мощность считается **локально**, не глобальным бесплатным числом для фракции.
- Малый стартовый генератор/станция + первый расширяемый тип (солнечная генерация допустима). У потребителя есть потребление в покое/работе; у источника — производимая мощность и состояние.
- Дефицит мощности имеет приоритеты нагрузки и наблюдаемый эффект: остановка/снижение темпа производства, очистки, верфи и т. д. Весь экономический цикл не должен умирать без механизма восстановления.
- Состояния/ресурсы энергосети и причины блэкаутов должны быть доступны API и Observer.
- Не внедрять электропроводку до отдельных блоков/комнат, охлаждение и аварии «как в SS13» в Genesis 0.1.

### 4.4 Верфь: корпус, оснащение, ввод в строй

- Отличать уже существующее производство модулей от отсутствующего производства **самих корпусов**.
- `ShipBuildOrder` (название условное): `id`, владелец, место верфи, класс/рецепт, стоимость/ресурсы, бюджет/резерв, состояние (`proposed → approved → waiting_inputs → building → completed/failed/cancelled`), `started_tick`, `end_tick`, `result_ship_id`, причина блокировки.
- Вход в `building` только после проверки доступности мощности, места/мощности верфи и материалов; стоимость и расход материалов реальны. Определить единый момент списания/резерва, не тратить дважды.
- Сборка имеет продолжительность, не `spawn_ship` на событии запроса. При успешном завершении создаётся ровно один корпус в ECS + его запись в БД, необходимый базовый fitting, топливо/допуски и владелец; после рестарта повторного создания нет.
- Не создавать корабль вне завершённого производственного заказа; исключения только явные *admin debug* вне режима Genesis.
- Списание старого корабля уменьшает флот, не создаёт бесплатного `PendingRespawn`.
- Базовая цена/рецепт должны быть достижимы стартовой экономикой; если нужно, дать фракции ограниченный стартовый резерв/кредит с объяснимым происхождением как условие initial seed, но **не регулярный бесплатный приток**.

### 4.5 Планирование фракции и администраторы

- **Глава фракции** выбирает один основной приоритет и допустимые вспомогательные: например, устойчивость снабжения, промышленность, транспортная ёмкость, энергобезопасность. Не выбирает на каждом тике случайные цели.
- **Администраторы** (достаточно 2–3 в 0.1) наблюдают потребности своей области и формируют **конкретные** проекты: увеличить выработку, построить модуль/корпус, доставить ресурсы, устранить дефицит, улучшить добычу. Области: производство, логистика, инфраструктура/энергия. Разведка/экспансия позже.
- Сформированный проект имеет `id`, инициатор, причина, целевая метрика, затраты, требуемые материалы/энергию, ожидаемый эффект, связанные задания, прогресс, статус, стоп-фактор, историю решений. Не генерировать проект лишь потому, что «прошёл час».
- **Арбитраж:** глава/планировщик одобряет только проекты в рамках ограниченных денег и запасов; резервирует конкретные ресурсы/бюджет, не позволяет двум проектам потратить один металл. Проекты с меньшим приоритетом ждут, а не обходят ограничения.
- **Исполнители** (существующий ship AI, production jobs, строительство) выполняют одобренные задачи. Нет второго параллельного симулятора «для презентации».
- Если проект упирается в отсутствие транспорта/энергии/технологии, причина видима, и создаётся минимальный план снятия блокировки; не бесконечная очередь невыполнимых проектов.
- Для 0.1 не нужна сложная LLM-логика, 10 министров, дипломатия, частные корпорации или политические войны. Простые проверяемые rules/utility-score предпочтительнее.

### 4.6 Сохранение и история

- `genesis.db` полностью отделён от `sim.db`, существующие сохранения не перезаписывать без явного запроса.
- Ключевые ID стабильно сохраняются: объект, корабль, товар/склад, строительный заказ, проект, событие, связанная причина.
- Значимое событие ссылается на реальное изменение состояния: `actor_id`, `subject_id`, `kind`, `tick`, `cause/project_id`, `before/after` там, где уместно. Красивые тексты можно делать уже на клиенте из фактов.
- Пауза останавливает симуляцию, но не уничтожает снимок данных. Перезагрузка браузера не меняет мир.
- Для критических операций нужна гарантия однократного применения при повторном вызове/рестарте.

## 5. Интерфейс — наблюдаемая причинность, не панель отладки

В долгосрочной структуре 4 взаимосвязанных контекста; для 0.1 достаточно минимально реализовать нужные части каждого. Приоритет **понятность работы маленькой экономики**, а не максимальное число функций.

| Контекст | Главный вопрос | Показать |
|---|---|---|
| **Сектор** | Где мы и куда расширяться? | Системы, известность, принадлежность, доступные переходы. Пока одна система — экран минимален, не главный в Genesis |
| **Система** | Что физически находится здесь и что происходит? | Реальные планеты/орбиты, месторождения, станции/верфи, корабли **только в реальном транзите** на карте, локальные потоки и предупреждения |
| **Экономика** | Где сырьё, энергия, дефицит, грузы и очереди? | Источники → транспорт → потребители, склады по локациям, производственные операции, потребление энергии, блокировки |
| **Фракция** | Что она решила, почему и к чему это приведёт? | Приоритет главы, проекты администраторов, затраты/резервы, исполнитель, прогресс и журнал причин/результатов |

**Плотность:** основной экран 1920×1080 без необходимости скроллить для обзора 3–5 важных объектов, интерфейс адаптируется на меньшие окна. Правый инспектор контекстный; не заслонять карту постоянной стеной текста. Сдержанный космический/sci-fi стиль, не стилизованная «нейросеть» с лишним декором. Визуальные элементы должны различаться без необходимости изучать легенду из 20 символов.

**Правила карты (по замечаниям с текущих скриншотов):**
- Позиция маркера связана только с авторитетными мировыми координатами сущности; сетка прикреплена к этим координатам.
- Зум относительно курсора. Координаты растягиваются с масштабом; размер значков меняется ограниченно, чтобы не захламлять экран. Подписи раскладываются без пересечений и не смещают сами объекты.
- Не изображать стоящие/пристыкованные корабли как рейсы: их показывать в списке своего хаба, а в пути — отдельными маркерами, по фактическим `transit` и `position`. Запрещено раскладывать их по визуальному кругу.
- Станция привязана к своему телу/локации, а **не** к кораблям. Если тело орбитально движется, станция может двигаться вместе с этим телом: это не следование за кораблём, но должно быть объяснимо по данным.
- Рисовать анимацию только если она соответствует движению агента, изменению работы оборудования, отправке/доставке груза. Никакой декоративной лживой «жизни».
- При выборе проекта/события показывать путь «почему → решение → реально выполненное действие → результат», с переходом к участвующим объектам.
- Не выдавать контекстный UI за отдельную сущность/склад/агента в сервере.

**Статус UI в текущей ветке:** Canvas-прототип пригоден для проверки. Дальнейший дизайн требует осмысленного отделения слоёв данных, маркеров, подписей, статуса кораблей и инспектора; косметическая смена палитры без переработки информации — не решение.

## 6. Архитектура для реализации

Существующий **источник истины** — Rust ECS и SQLite, а не браузер. Рекомендуется развивать текущую структуру, а не переписывать проект:

- `crates/sim_core/src/economy/commodities.rs`, `recipes.rs`, `module_production.rs`, `contracts.rs`, `order_book.rs` — каталог ресурсов/реальная цепь/цены/задания.
- `crates/sim_core/src/agents/facility/` и `agents/celestial_body.rs` — добыча, переработка, месторождения и локальная инфраструктура.
- `crates/sim_core/src/agents/ship/` — реальные состояния судов, груз, рейсы и автономные решения. Не путать `ShipSnapshot` и источник истины.
- `crates/sim_core/src/agents/faction.rs` — состояние/финансы фракции, новые решения планировщиков — **в отдельном модуле**, а не в HTML.
- `crates/sim_core/src/simulation/spawner.rs` и `crates/sim_server/src/engine/drains.rs` — обнаружить бесплатные respawn, отключить в Genesis безопасно (сохранить старый режим).
- `crates/sim_server/src/engine.rs`, `snapshot.rs`, `http/api.rs`, `runtime.rs` — фазы тика, снимки, API, стартовый сценарий.
- `crates/sim_db/src/seeder.rs`, `spawner.rs`, `persistence.rs` — seed, загрузка, сохранение и миграции. Миграции не разрушают старые сохранения.
- `observer/app.js`, `observer/model.js` (+ тесты) — отображение, интерактивность и адаптеры; **не моделировать здесь экономические причины**.
- `priv/genesis/data/`, `Start-Genesis.cmd` — изолированный тестовый мир и запуск.

**Важное инженерное решение до кодинга:** установить *один* авторитетный реестр товаров/локальных запасов, чётко определить момент бронирования/списания, и **не** дублировать экономическое состояние между `MarketPricing.supply`, `FacilityStorage.reserves`, грузом и новой складской таблицей. Сначала аудит, затем миграция и проверка баланса.

**Интеграция:** small, testable changes; новые фазы/структуры только после выбора места в tick; завершение заказа через идемпотентную команду и DB. Не создавать новый standalone backend/frontend или Godot-приложение. Сохранить MIT LICENSE, атрибуцию и возможность возвращаться к upstream.

## 7. Очередь работ — маленькими PR

Каждый шаг завершён **только** если есть код, тесты и наблюдаемый результат. Промежуточные PR держать пригодными для запуска, в своей ветке, не зашивать «половину фичи» скрытым автоспавном.

| Этап | Что сделать | Проверяемый результат |
|---|---|---|
| **P0. Базовая инвентаризация** | Клонировать нужную ветку; сравнить реальное состояние кода с этим документом; Windows headless smoke; зафиксировать DB-снимки/контракт API и заводскую цепь. | Новый мир = 1/1/3 и ожидаемые тела, facilities, markets; пауза/рестарт не теряет ничего; известны источники всех бесплатных спавнов/регена |
| **P1. Антимагия логистики** | Сформулировать единые локальные запасы и инварианты; привести существующие pickup/delivery/recipes к согласованному учёту. | При перевозке товар не одновременно в источнике, судне и пункте назначения; недостача останавливает исполнение; сохраняется после рестарта |
| **P2. Небольшая реальная добыча** | Минимум 2 вида руды; ограниченное месторождение; реальная добыча, переработка и доставка в промышленность; минимальное знание/оборудование. | Руда появилась только после физического извлечения; месторождение теряет запас; компонент появился после переработки и доставки |
| **P3. Энергия** | Локальная генерация и нагрузки, энергобаланс, ограничение рецептов/верфи, проект устранения дефицита. | При нехватке энергии реальное производство замедляется/стоит; новый генератор снимает блокировку без бесплатного ресурса |
| **P4. Реальное строительство корпуса** | Заказ корпуса + материалы, энергообеспечение, бюджет, время, монтаж базовых систем, запись в БД, исключение автоспавна. | Старт 3 корабля → после завершения заказа 4; потрачены материалы/деньги/время; новый корабль выполняет задания; при рестарте остаётся 4 |
| **P5. Иерархия решений** | Глава выбирает приоритет; 2–3 администратора предлагают и согласуют проекты, резервы, блокировки и выпуск заказа на верфь. | Строительство P4 инициировано экономической потребностью фракции, **а не** кнопкой debug/запрограммированным «создай на тике 500» |
| **P6. Observer причин и производства** | Минимальные экраны «Система / Экономика / Фракция», цепочка событий/проектов с кликом в объекты; сохранить обзор Сектора. | Пользователь без логов понимает, кто/почему/чем занят и где узкое место; реальный проект можно проследить до выпуска корабля |
| **P7. Стабильность и сборка** | Интеграционные, повторные запуски, негативные сценарии, ускоренный прогон, полный Windows ZIP без поиска Artifacts. | Закрыта матрица проверки §8, отдельный `genesis.db`, полная сборка, нет критических «спавнов из воздуха» |

**Приоритет:** первый полностью работающий путь важнее одновременной реализации десятка механик. Если P2/P3/P4 потребуют существенного refactor — предложить самый узкий вертикальный вариант с сохранением физических инвариантов и понятным расширением.

## 8. Приёмочные проверки / Definition of Done

**Обязательно автоматизировать на доступном уровне (unit + интеграционные + Windows smoke):**

1. **Изоляция:** новая Genesis DB → 1 система, 1 фракция, 3 корабля; большой `sim.db` не меняется. Перезапуск не досевает новые/лишние корабли.
2. **Пауза:** остановка на разных тиках (включая не кратные 4/16) не делает `/api/report` пустым; при паузе состояние остаётся прежним.
3. **Происхождение товаров:** тестовые товары возникают только по процессам с явными затратами/источниками; пофазная сверка суммарного количества товаров с учётом производства, потерь и месторождений.
4. **Реальная перевозка:** без доступного корабля, вместимости или топлива поставка невозможна; в рейсе товар не присутствует одновременно в двух складах; доставка увеличивает только нужный склад.
5. **Дефицит:** отсутствующий металл/энергия/компонент реально блокирует заказ и отображается как конкретная причина; доступность снимает блокировку.
6. **Неудвоение:** повторная доставка, повторное завершение заказа, остановка/загрузка между фазами не удваивают предметы/корабли/кредиты.
7. **Корабль из верфи:** выполненный заказ потребляет рецепт/время/кредиты, создаёт ровно одного нового ShipAgent с уникальным ID и базовым комплектом; новый агент способен действовать.
8. **Без автоспавна:** списание корабля в Genesis уменьшает число кораблей; старый большой режим при необходимости сохраняет исходное поведение (regression).
9. **Решения:** у заказа есть проект/обоснование, автор, бюджет и блокировки; разные проекты не резервируют один ресурс сверх имеющегося.
10. **Сохранение:** состояние после `N ticks → shutdown → resume → M ticks` соответствует непрерывному ходу на выбранных инвариантах (оговорить RNG / nondeterminism и измерить, а не обещать полную побитовую идентичность).
11. **Карта:** точный world-grid, масштаб к курсору, станция не следует за кораблём, пристыкованные показаны у станции, в пути показаны по фактическому `transit`. Перезагрузка UI не влияет на мир.
12. **Наблюдаемость:** хотя бы один реальный цикл «потребность → проект → поставка → производство → корпус → новый рейс» читается без открывания Rust-логов.
13. **Windows:** готовый ZIP с EXE, `Start-Genesis.cmd`, `observer/`, `priv/genesis/data/`; пользователь просто распаковывает и запускает. Передача полной сборки — ссылкой на ZIP прямо в чате, патча — если менялись только UI/документы.

**Не требовать буквально 100% детерминизма**, пока исходная база его не гарантирует; вместо этого описать конкретную недетерминированность и защитить экономические инварианты.

**Неприемлемо:** убедительный интерфейс при невыполненной цепи, free respawn, виртуальные корабли только в снапшоте, скрытое перенесение товара, формальные «администраторы» без задач/резерва ресурсов.

## 10. Вопросы для короткого обсуждения с Codex (не блокируют старт аудита)

**Вопрос 1 — единственный склад.** Текущий `MarketPricing.supply` может остаться общим локальным складом, либо нужен отдельный складской компонент с адаптером к рынку. Попросить Codex сравнить **риски, миграции и гарантию одного источника истины**. Рекомендация: минимально переделать существующую экономику, без нового дублирующего реестра.

**Вопрос 2 — виды руды.** Какие 2–3 типа впишутся в существующий `Commodity` и `recipes` с минимальными каскадными поломками? Оставить 0.1 на доступных базовых рудах; знания/особое оборудование — небольшое ограничение, не огромное древо.

**Вопрос 3 — приоритет генератора и верфи.** Какой самый малый реальный энергобюджет и достижимый рецепт корпуса обеспечат «3→4 корабля» без тайных субсидий? Попросить предложить измеримые параметры для seed.

**Вопрос 4 — planner vs existing ship AI.** Где правильная граница между фракционными проектами и существующей торговлей/контрактами? Не создавать второго механизма доставки, если старый можно встроить.

**Вопрос 5 — granularity реализации.** Сколько узких PR необходимо, чтобы сохранить работающий билд после каждого? Если есть риск многочасовой компиляции после каждого UI edit, разделить быстрые Node/симуляционные тесты и редкую Windows native сборку.

**Без новых согласований можно:** провести аудит, предложить план PR, исправить очевидные ошибки отображения/сохранения, добавить тесты. **На краткое согласование вынести:** новую схему складов, правила руд, баланс энергии, рецепт нового корабля, приоритеты фракции. Если владелец недоступен, описать разумные варианты и выбрать наименее разрушительный **для прототипа**, не маркируя его как утверждённый закон игры.

## 11. Как передавать задачу и как отчитываться

1. Codex сначала читает `AGENTS.md`, этот файл, `GENESIS_0_1_STATUS.md`, `DESIGN.md`, `ARCHITECTURE.md`, `HANDOFF.md` и **живые исходники**; уточняет актуальную ветку/коммит. Не верит устаревшим README и анализу 3D Godot-прототипа.
2. Создаёт **отдельную ветку** от `feature/genesis-0-1` (например `codex/genesis-economy-p0`), с небольшим PR обратно в `feature/genesis-0-1`; ничего не merge/force-push без разрешения.
3. Сначала выдаёт **короткий аудит (10–15 пунктов)**: что переиспользуется, что не работает, какие файлы изменятся, план шагов и предполагаемые проверки. Затем работает по этапам в приоритетном порядке; вопросы только по принципиальным открытым решениям.
4. На каждом PR: цель, изменённые модули, результаты тестов (с точными командами), **непроверенные** части, риски совместимости БД, статус следующего этапа; актуализирует `docs/living-sector/STATUS.md`. Не заявляет «готово», если тесты не запускал.
5. Для пользователя сборки: **готовый ZIP прямо в диалоге**, последней строкой, когда build доступен; UI-only патч — отдельно. Не отправлять владельца вручную искать GitHub Actions Artifacts, если можно прикрепить архив.

**Ожидаемая цель первой сессии Codex:** аудит P0, проверяемая архитектура ресурсов/корпуса/энергии/планировщика, список последовательных небольших PR, старт первого нужного исправления. Не тратить первый день на палитру, создание нового HTML-макета или подготовку огромного каталога звёзд.
