# F0 — технический аудит денежных потоков S7 (для Work/F1)

> **Дата:** 2026-11-06. **Основание:** \`feature/genesis-goal-options\` @ \`31f29e719e8d734e6780e331acfe732cd3098c62\` (PR #23).  
> **Статус:** **статический аудит исходного кода**, без изменения движка, без компиляции или runtime-инвариантного прогона. Не утверждать, что ниже покрыты все пути исполнения. При работе F1 пройти повторный grep по репозиторию и проверить фактический порядок тиков.  
> **Политика денег:** банки, кредиты, проценты, эмиссия и бесконечные кассы запрещены решением владельца. **Но аудит наследуемого кода обязан зафиксировать прежние скрытые источники/стоки**, даже если они существуют лишь в устаревших или незапущенных сценариях.

## Самое важное для Work

Не начинать с исправления одной строки \`SellAll\`: выявлены **несколько независимых необеспеченных путей**, а часть дорог уже реализует правильную компенсационную проводку. Нельзя удалить существующие escrow/контракты/SQLite-кадры и переписать их вторым ledger.

**Граница решения владельца:** обычная продажа возможна только при наличии **реального покупателя** с реальными средствами. Рынок — место сопоставления заявок/цен, а не самостоятельная бесконечная казна. Не принимать отдельные экономические решения из старых промптов без перепроверки последних указаний пользователя.

## Карта операций: подтверждённый код

Статусы: **paired** — есть явное списание и начисление; **unpaired** — отсутствует реальная денежная вторая сторона; **conditional** — зависит от типа контракта или параметра; **model gap** — нет денежных участников / требуется согласование; **sink** — сознательное изъятие, несовместимое с полностью фиксированной массой, если не заменить на получателя. Порядок строк не является порядком вызовов в tick pipeline.

### Отдельная физическая проблема (не смешивать с денежным F1)

\`market.rs:307–325\` также содержит \`flow.production/consumption\`, которые напрямую прибавляют/убавляют товар в общем \`MarketPricing.supply\`. Прежде чем вводить новую добычу с коэффициентом 0,3–0,5, классифицировать *источник ресурсов*, *производственный рецепт* и *потребителя*: иначе тест денежной сохранности может пройти при неучтённой физической эмиссии. Это **другой** инвариант; не заставлять Work переписывать добычу в F1.

## Уже существующие гарантии — не переписывать

- \`transactions.rs:236–319\`: проверка наличности, реального остатка и вместимости трюма перед mutating buy.
- \`contract_funding.rs:109–170\`: нельзя принять невыполнимую доплату funded-контракта; claim и резервируются только после предварительных проверок.
- \`contract_funding.rs:172–214\`: возврат незадействованного escrow в реальную кассу (если счёт существует).
- \`persist.rs\` + \`sim_db/src/persistence.rs\`: \`EconomicFrame\` собирает изменения счета/контракта; частичный commit не должен сохранять выплату без дебета.
- \`drains.rs:455–463\`: стартовый капитал построенного предприятия переводится из реальной фракционной казны.
- \`faction.rs:431–456\`: налоги переводятся между существующими кошельками.

**Не утверждать, что этих гарантий достаточно для всей игры**: \`ShipAction::Sell\` и \`market.TransferCredits\` обходят их.

## Предлагаемая исходная формула для теста Work/F1

\`\`\`text
M_accounts = Σ ship.credits
           + Σ facility.credits
           + Σ faction.treasury
           + Σ population.total_wealth   [if treated as money]
           + Σ contract.funding.reserved
           + Σ crew.wages_credits        [only if a real, durable claim]

delta_M = M_after - M_before
\`\`\`

Нельзя считать формулу завершённой без выяснения, где живут crew wages, legacy advance, admin-created balances и существующие fee burns. В **строгом режиме без эмиссии и изъятия** каждое нормальное событие должно иметь \`delta_M=0\`. Для контрольного S7 снимка в текущей реализации \`delta_M\` **может быть ненулевой**, что и является частью исходного диагноза; не скрывать это нормализацией.

**Точки наблюдения:** до/после каждого типа операции + стабильный счёт на старте/конце тика, в состав которого входит escrow. Отдельно суммировать необеспеченные начисления, fee burns, внешние административные зачисления и миграции. Не пересчитывать богатство населения как «новую валюту», если оно пока не связано с настоящими платежами.

## Минимальные адресные тесты, которые Work обязан дописать

1. \`Sell\` и \`SellAll\` с товаром, но без платёжеспособного покупателя: **не** уменьшается cargo, **не** растёт ship cash, **не** увеличивается market supply.
2. Реальная продажа: \`−payment\` у покупателя, \`+payment\` у корабля, \`ΔM=0\`; stock \`−qty/+qty\` строго однократно.
3. Одновременная продажа двумя кораблями при бюджете только одного: ровно один платёж, второй — понятный отказ/частичная сделка.
4. Market spread \`TransferCredits\`: нет одностороннего начисления; комиссия, если остаётся, идёт из реально удержанной суммы.
5. Funded contract: \`payer → escrow → ship\`, необеспеченный contract accept отклонён без изменений, expire возвращает точно остаток.
6. Legacy/population contract: отсутствие финансирования явно видно; без реального плательщика корабль не получает base reward.
7. Зарплата экипажу: \`money_after=money_before\` с правильно классифицированным получателем; save/restart не уничтожает/не удваивает выплаты.
8. Налог и emergency bailout: \`ΔM=0\`; предприятие и фракция после rollback/отказа в исходном состоянии.
9. Docking burn: тест точно фиксирует текущую дельту и позволяет сменить политику после согласования; не прятать в аварийной эмиссии.
10. Симуляция нескольких циклов торговли по одной цепочке с сохранением/restart; одна операция не применяется повторно.

## Ограничения этого отчёта

- Этот файл подготовлен **по чтению исходников**, не по запуску нового тестового мира, и не доказывает число реально выполненных операций каждого типа.
- \`PopEconomy\` уже присутствует в коде, но стартовый набор Genesis может не создавать население; отсутствие экземпляров в конкретной БД **не** означает отсутствия модуля.
- Не найденный здесь путь не становится автоматически корректным. F1 должен самостоятельно пройти весь охват и зафиксировать пробелы.
- Решения, которые пользователь вносит в другом чате, могут менять **будущую модель**, но не перечисленные факты исходного S7; перед реализацией сверить новые решения.
