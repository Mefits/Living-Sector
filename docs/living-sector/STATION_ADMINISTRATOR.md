# Station Administrator — A1 и контракт следующего блока

2026-11-07. Ветка `feature/genesis-station-administrator`, PR #41.
База: unified `fd4e3315f5502aa4c02619b8f84629997183f422`.
Пользователь отложил новые финансовые механики и подтвердил архитектуру:
один администратор на все модули станции; фракционные корабли исполняют его
приказы, независимые выбирают контракты; миграция требует транспорта.
Это актуальный приоритет вместо дальнейшей настройки финансов/персонала сервисов.

## Сделанный функциональный блок

1. Один runtime-администратор на пару `(faction_id, location)`. Все существующие
   Facility-модули этой пары входят в снимок; чужая фракция не получает её работников.
2. Наблюдение за населением, уже оплаченными сменами, состоянием модулей, локальными
   запасами, сырьём для рецептов, доступной добычей, существующими бюджетами и
   выбранной проблемой главы. Нет отдельного склада, кошелька или населения.
3. Сравнение производственных вариантов: актуальность выпуска по запасам/дефициту,
   усиление приоритета главы, проверка рецепта/геологического ресурса/владения складом.
   Невыполнимый вариант сохраняется с причиной; ожидание выражено незанятыми людьми.
4. Назначение целых рабочих команд модулям в порядке полезности. Если людей хватает,
   высокий запас сам по себе НЕ останавливает производство: нет нового порога
   «слишком много еды». Запасы влияют на выбор только при конкуренции ресурсов.
5. Инерция назначения: 15% к оценке ранее выбранного жизнеспособного модуля.
   Сильная новая потребность перебивает её; невыполнимое назначение бонус не спасает.
   Это небольшая, изменяемая политика, не жёсткая последовательность действий.
6. Исполнение через существующий payroll: не назначенному производственному модулю
   отказывается в смене до изменения денег и запасов. Проверки native ресурсов
   остаются последней инстанцией. Финансовый резерв на будущие периоды не вводится.
7. Обратная связь разделяет assigned_workers и actual_workers. Причины последнего
   native отказа публикуются отдельно от причины выбора администратора.
8. Нехватка входов даёт диагностический Need (`supply_input`), пригодный для
   следующего слоя диспетчеризации. Это НЕ приказ, контракт или бронь ресурсов.

## Глава → станция → исполнители

A1 читает `head.problem`, усиливая выпуск нужного товара именно в целевой локации.
Это первое подключение направления главы, не полный портфель директив. Администратор
решает локальное распределение, не присваивает себе право тратить казну на новые
проекты. Старые логистический/строительный администраторы фракции пока работают как
ранее; A2 должен согласовать их с локальными заявками, не создавать дублирующие заказы.

Сейчас управляется персонал штатных рецептов и добывающих предприятий. Все модули
видны, но доки, ворота, выпуск корабельных модулей и отдельные сервисы отмечены
`outside_production_scope`. Их нельзя считать административно управляемыми только
из-за присутствия в снимке. Саморемонт выполняется раньше A1 и его оплаченные люди
уже исключены из доступных; строительство использует оставшихся по механике F3/F4.

Команда назначается целиком: частичная производительность предприятий ещё не
добавлена. Физический состав населения/его местоположение не меняются. При нехватке
местных людей администратор не берёт работников другой станции.

## Точки интеграции

- `strategy/station.rs`: наблюдение, сравнение, распределение, feedback.
- `agents/facility/mod.rs`: plan после ремонта/restock и перед recipes/mining;
  feedback после производства на том же native рабочем каденсе.
- `agents/facility/workforce.rs`: исполнение проверяет назначение в execute;
  сама зарплата и распределение по PopEconomy остаются прежними.
- `sim_server/src/snapshot.rs`: добавляет `stations[]` в `/api/strategy` v1.
  Старые поля не переименованы. Observer не изменён.
- Состояние решений transient, как существующая стратегия. После рестарта план
  восстанавливается из ECS и сохранённых смен. Сохранённые смены текущего тика
  учитываются как уже работающие, повторной зарплаты нет. Инерция выбора после
  рестарта начинается заново; точный replay истории решений не обещается.
- Shadow показывает рекомендации, но НЕ блокирует native производство. Execute
  включает назначения. Не трактовать shadow actual_workers как исполнение решения.

## API для независимого Observer

`stations[]`: faction_id, location, observed_tick, executing, workforce,
already_working, assigned_workers, idle_workers, head_priority, modules[], needs[].
Все счётчики людей относятся к рабочему тику observed_tick, не к постоянному найму.

`modules[]`: facility_id, facility_type, required_workers, assigned_workers, score,
priority_commodity, head_priority, retained, reason, actual_workers, execution_reason.
`retained` означает бонус прежнего назначения, а не гарантию выбора/исполнения.

`needs[]`: facility_id, commodity, kind=`supply_input`. Количества, маршрута,
исполнителя и состояния приказа пока нет — в UI показывать «—», не вычислять их
как будто сервер уже назначил перевозку. Отдельные выпуск/расход за период не добавлены.

## Проверки и ограничения

Проверенный код: `7931daaa0f98dc81110979fab4903efff2494d16`.
[CI 42380994557](https://github.com/Mefits/Living-Sector/actions/runs/42380994557) прошёл:
7 station_admin проверок, адресные workforce и SQLite construction checkpoint,
тестовый genesis_server и короткий API/native payroll smoke. Релиз/Windows не
собирались. Первый прогон прошёл core-проверки, но smoke использовал устаревшее
ожидание 6 групп населения; теперь количество сверяется с seed всех систем.


Адресно проверяются изменение реального производства при дефиците персонала,
сохранение суммы денег, смена приоритета, инерция, shadow без управления, отсутствие
денег/сырья, локальность населения, направление главы и восстановление плана из
native записи смены. Последняя проверка удаляет transient ресурс на том же World;
реальный SQLite зарплат/стройки проверяется существующими focused checkpoint-тестами.

План использует снимок ресурсов. Между двумя предприятиями могут конкурировать
входы одного склада: распределение персонала не является резервированием сырья.
В этом случае native исполнение отказывает, фактическая работа отличается от плана,
а следующий рабочий тик пересматривает варианты. Внутри модуля набор штатных рецептов
пока не меняется: priority_commodity объясняет приоритет модуля, а не новый приказ
выпускать только один товар. При LOD-паузе назначенные люди могут фактически не работать.
Это наблюдаемые ограничения A1, не повод объявлять всю станцию автономной.

## Следующий крупный блок A2

Цель: решение → приказ → реальный фракционный исполнитель → результат → пересмотр.
Отдельный модуль диспетчеризации должен владеть стабильными order_id, station key,
типом задачи, целевым объектом/товаром, количеством, executor_id, состоянием,
причиной остановки и номером попытки. Значения выводить из native объектов; не
дублировать груз, деньги или население. Приказы должны переживать SQLite checkpoint
и не допускать двойного назначения корабля. Это требования интерфейса A2, а не
объявление перечисленных полей уже реализованными в A1.

Фракционные корабли следуют назначениям, но сохраняют native навигацию, заправку,
безопасность и обработку неудач. Независимые сохраняют контрактный выбор. Миграция
только после физической перевозки. Совместить локальные Need с существующими
предложениями главы/контрактами, прежде чем включать новые списания или диспетчеризацию.
