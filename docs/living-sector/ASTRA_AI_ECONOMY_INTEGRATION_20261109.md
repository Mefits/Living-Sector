# ASTRA — объединение C1 + Balance v1.0 + AI Decision Bench v1.3
**9 ноября 2026 · handoff / интеграционный контракт · НЕ готовый релиз**

## Суть задачи
Разработать **одного рабочего стратегического ИИ фракции**, составленного при необходимости из разных планировщиков, поверх настоящей симуляции Genesis; не писать второй движок и не переносить прототипные числовые баллы как игровой смысл.

Владелец просит минимум этапов, ограничение лимитов, сохранение рабочих механик, **никаких автоматических GitHub Actions / Windows-релизов** до запроса.

## Точка продолжения
- Репозиторий: `Mefits/Living-Sector`.
- Игровая база: `feature/genesis-c1-colonization` (в C1 уже A1/A2, F1–F4, основание станции, SQLite).
- Рабочая интеграционная ветка: `feature/genesis-portfolio-advisor-shadow-20261109` **от C1**. Содержит новое исследовательское ядро. **Оно пока не компилировалось/не тестировалось Rust-компилятором в текущей среде и НЕ должно попасть в стабильный билд без исправления возможных ошибок.**
- Ветка `main` существенно старее Genesis — не выбирать её источником для слияния.
- Оригинальный Windows-билд C1, `Living-Sector-Balance-Optimizer-Galaxy-v1.0.zip`, `Living-Sector-Galaxy-AI-Decision-Bench-v1.3-Windows-x64.zip` находятся в отдельном комплекте.

## Что реально существует
| Слой | В нативном Genesis C1 | Только в исследованиях |
|---|---|---|
| Мир | 6 тестовых систем, три фракции, реальные корабли, станции, колонизация | 100-системные случайные галактики |
| Экономика | 13 товаров, 10 рецептов, F1–F4: сделки, платные смены, постройки и транспорт | 18 товаров, 29 сооружений T1–T4, экспериментальные цены, солнечная энергия и полный научный граф |
| ИИ | глава S7, администратор A1, приказы A2, BT-исполнители, C1 колонизация | HTN 0.2.1, Telic 0.1.0, Cranium 0.3.0, Beam; 15 прогонов на упрощённой модели |
| Новые файлы в интеграционной ветке | `strategy/portfolio_policy.rs`, `strategy/production_dependencies.rs`, read-only поля `head.shadow_portfolio`, `head.native_chain_probe` | Нет интеграции HTN/Beam/Cranium в исполняющие системы |

Важно: `production_dependencies` **лишь строит предполагаемую последовательность по реальным рецептам**, с учётом складских остатков и альтернативного топлива. Это не выполнимый заказ, пока не проверены производство, время, рабочие, инфраструктура, транспорт и исследование. `native_chain_probe` рассматривает **только 10 единиц** нужного товара как диагностический пример, а не весь дефицит.

## Результат сравнения фреймворков (не выбирать победителя по нему)
Данные `summary(7).json`: 3 сценария × 5 методов × 140 решений. HTN во всех 420 решениях ждал; Control Beam, Telic Beam и Cranium+Telic внутри каждого сценария имели идентичные action_trace. Ни один метод не открыл T2. Итоговый score включает штраф за **различную длительность действий**, поэтому быстрее действующий Cranium выглядит победителем, хотя прогресс технологии нулевой. Фреймворки **пока не получили честный тест на реальной игре**.

## Два крупных блока работы

### Блок А — исправить и завершить нативный узкий срез
1. Провести локальную компиляцию и быстрые тесты ветки (никаких автоматических Actions без отдельного разрешения): `cargo test -p sim_core production_dependencies`, `cargo test -p sim_core portfolio_policy`, адресные `strategy_block_head_` и `cargo test -p sim_server autonomous_colonization_and_restart`. Если надо, исправить добавленный экспериментальный код, но не менять текущие исполнительные правила C1.
2. На реальной существующей цепочке `Ice/Gas → Fuel; Ore+Fuel → Metals; Gas → Polymers; Metals+Polymers → Components; Components+Metals → Electronics` проверить выбор главы, потребности A1, оплаченные смены, контракты A2 и журнал фактического выполнения. Эта цепочка доступна **из нативных рецептов**, искусственный ресурс не нужен.
3. Встроить **один** маленький реальный T2-вертикальный срез после T1: одно исследование металлургии T2, реальный unlock, **один** завод сплавов, реальное производство `alloys` с расходом сырья, энергии и труда. Для этого аккуратно добавить минимум отсутствующих товаров (`rare_ore`, `energy_cells`, `alloys` — когда требует реализация), поддержать сохранение и показ в минимальном UI. **Не устанавливать сразу все 29 зданий, 92 технологии, 100 систем или SVG-ассеты.** Цены брать из draft только как исходную гипотезу и документировать единицы. Солнечная генерация T1 должна запускаться без требования уже изготовленной энергии.

### Блок Б — интегрировать и проверить управление, не переписывая игру
1. Общий интерфейс «наблюдение → возможные намерения → проверка предусловий → сравнение прогнозов → один санкционированный заказ → исполнение BT/A2 → обратная связь». Только **системы Genesis** имеют право менять деньги/запасы/население. Фреймворк лишь предлагает действия.
2. Стратегический выбор приоритетов — Utility; планирование зависимостей — небольшой HTN; сравнение 2–4 выполнимых вариантов — ограниченный Beam (гибрид — **рабочая гипотеза**, не догма). Существующие A1/A2/BT не заменять; наличие HTN/Beam определять по измеримому улучшению. Сначала shadow, потом переключение через флаг; ни один альтернативный планировщик не должен незаметно менять состояние мира.
3. Один тестовый мир C1, несколько независимых стартовых seed/кризисных вариантов. Сравнивать с текущим главой **за одинаковый игровой горизонт**, учитывая: реальное производство электроники/сплавов, построенные станции, население, снабжение, научные открытия, долговременную обеспеченность и кредитную сохранность. Не начислять очки за повторное производство без спроса. Отдельно считать задержку планировщика, ошибки и зацикливания.
4. Подготовить один проверяемый PR с результатом, списком изменений и инструкцией отката. Пока нет реального T2 и долгого сквозного прогона — НЕТ статуса «готово к игре».

## Обязательные границы
- **Никаких** бесплатных генераций товаров/кредитов, прямых изменений запасов из AI, обхода escrow/SQLite, дублирования исполнителей, миграции без корабля, внезапного respawn ресурсов.
- Не смешивать `bench ticks` со временем игры, `resource lot = 100` с нативными единицами, или экспериментальные здания с существующими facility types.
- Сохранить C1 тесты автономного основания станции и обязательность физического прибытия кораблей.
- Никакого обязательного рисования SVG зданий до рабочего производственного среза: сначала нейтральные иконки/подписи.
- Не запускать длинные многодневные стресс-тесты до коротких адресных проверок.
- Исключить бездумный merge в `main` или релизный ZIP.
