## P1e: удаления вместе с контрактами — 2026-11-05

- Ветка `feature/genesis-lifecycle-checkpoint` поверх P1d `3a821f0` (draft PR #13).
- Удаления корабля/сооружения и запись retirement теперь остаются в очереди
  ECS до принятия полного EconomicFrame вместе с доской контрактов и балансами.
  Заполненный persistence-канал не блокирует admin-handler и не теряет удаление.
- На паузе движок также возвращает закрытые резервы и пытается отправить пакет
  удаления, не увеличивая tick. Отказ admission сохраняет очередь до следующей
  итерации. При исчезнувшем плательщике резерв по-прежнему не выдумывает получателя.
- Worker применяет tombstone после update/upsert в одной SQLite-транзакции:
  старая запись стройплощадки не воскресит её из-за порядка HashMap.
- Изменены engine/admin, persist, paused loop, DB flush ordering; добавлены
  2 теста: корабль/станция с escrow при backpressure и удаление стройплощадки
  после устаревшего upsert. CI выполняет только `lifecycle_` для этой ветки.
  Локально Rust отсутствует; `git diff --check` выполнен. **CI Linux: компиляция
  и 2/2 теста lifecycle_ прошли** для `a5773b6`:
  https://github.com/Mefits/Living-Sector/actions/runs/42090258777.
- Проверка восстановления выявила отдельный дефект: Accepted-контракт после
  загрузки имеет current_bt=None и освобождается как ghost_bt; навигационный
  emit также не сохраняет полный transit/location/docked state. Это не исправлено
  данным блоком, фиксированная награда не гарантирована через такое восстановление.
- Прямое создание materialization/admin/respawn всё ещё вне EconomicFrame;
  удаление source site упорядочено, но INSERT сооружения ещё не атомарен с ним.
  Остальные прежние границы полного checkpoint сохраняются.
- Далее: навигационное состояние и возобновление принятого рейса; затем создание
  объектов без разрыва между SQLite INSERT, ECS и контрактной доской.

## P1d: согласованная запись экономического тика — 2026-11-05

- Ветка `feature/genesis-economic-checkpoint` поверх P1c `4c9c2d3` (draft PR #12).
- Сервер заранее резервирует одно место в очереди, затем передаёт весь пакет
  dirty-состояний, доску контрактов и номер тика. При переполнении очереди
  dirty-флаги остаются; раздельные частоты записи экономических сущностей убраны.
- Worker объединяет только целые пакеты, без await между их частями. Дельты
  старых пакетов сохраняются, если следующий пакет не содержит эту сущность.
  SQLite commit включает кошельки, товары, резерв контрактов и tick вместе.
- При ошибке SQL транзакция откатывается, буфер сохраняется для повтора.
  Save-as дренирует уже принятые сообщения и получает подтверждение только
  после успешного commit; закрытый канал flush больше не вызывает busy loop.
- Изменены engine/persist, комментарий engine и sim_db/persistence. Добавлены
  2 адресных теста: backpressure и rollback/retry с реальной SQLite и загрузкой
  контрактов; CI workflow запускает только фильтр `checkpoint_`.
- Локальный `git diff --check` выполнен. Rust/Cargo в восстановленном окружении
  отсутствуют, локальные компиляция и Rust-тесты **не выполнены**.
  **CI на Linux успешно скомпилировал код и выполнил 2/2 проверки checkpoint_**
  для `d8513cd`: https://github.com/Mefits/Living-Sector/actions/runs/42087942838.
  Полный набор, soak и Windows-сборка не запускались.
- Граница: это согласованность штатного emit-пути для помеченных dirty данных,
  не полный replay/checkpoint мира. Прямые SQL admin/materialization, удаления,
  очередь команд/квитанции, RNG/BT и аудит всех dirty-writers ещё вне гарантии.
  Несохранённые тики при аварии могут быть потеряны; при финальной ошибке записи
  worker логирует ошибку и завершает работу. Полный graceful shutdown ещё отдельный.
  Новая частота сериализации увеличивает CPU/память очереди, нагрузка не измерена.
- Далее: объединить lifecycle/admin записи с границей checkpoint; проверить
  восстановление местоположения/активных заданий, затем claims и shadow AI.

## P1c: резервирование контрактной оплаты — 2026-11-05

- Ветка `feature/genesis-contract-escrow` поверх P1b `3026883` (draft PR #11).
- Новые предоплаченные контракты сооружений/фракций получают явный резерв
  базовой суммы. Принятие через подтверждаемую транзакцию резервирует недостающую
  сумму с надбавками и фиксирует выплату до завершения рейса. При нехватке денег
  контракт остаётся Posted, корабль не начинает выполнение.
- Доставка расходует резерв; последующее обнуление кошелька заказчика или
  изменение цены предложения не меняет согласованную оплату. Освобождение
  контракта сохраняет резерв, но снимает фиксацию цены для следующего исполнителя.
- Отмена/истечение и остаток после выплаты возвращают деньги один раз.
  Если счёт заказчика исчез или переполнен, резерв сохраняется для восстановления.
- Миграция SQLite 014 сохраняет funding_json и renewal_count; старые строки
  остаются без доказанного резерва и используют прежнюю схему P1b. Контракты
  населения не объявляются обеспеченными. Счётчик продлений больше не обнуляется
  при загрузке.
- Изменены native posting в facility/faction, contracts, ship actions/transactions,
  общий server apply/contract_funding/transactions и DB migration/persistence/spawner.
- Проверено: компиляция sim_core/sim_db/sim_server; **5/5 точечных тестов**
  (`cargo test --locked -p sim_core -p sim_db -p sim_server --lib escrow_`):
  ожидание BT, резерв и фиксированная выплата, конкуренция за бюджет, возвраты
  при отмене/истечении/потере груза и настоящий SQLite roundtrip. Проверка diff
  выполнена. Полный набор, soak, Windows-сборка и UI не запускались.
- Граница: сериализация резерва не делает периодические снимки контрактов и
  dirty-записи кошельков единым checkpoint. Аварийный перезапуск ещё может
  восстановить разные моменты состояния; exactly-once после сбоя не гарантируется.
  Планировщик также ещё может повторно выбирать неплатёжеспособное предложение.
- Далее: согласованный checkpoint денежных остатков и контрактов, оставшиеся
  источники финансирования/операции, затем claims и shadow-режим стратегии.

## P1b: снабжение производства и оплата — 2026-11-05

- Ветка `feature/genesis-production-supply`, база P1a `4859462` (draft PR #10).
  Предыдущие PR не сливались и не переписывались.
- Потребности заводов/переработчиков теперь выводятся из `RECIPES`: переработчик
  учитывает лёд, завод — компоненты и воду; лишний лёд у завода и топливо
  в рецепте фермы убраны. Сервисные запасы топлива учитываются отдельно.
- В дробных производственных партиях убрано округление расхода и выхода до
  целых единиц. Пример: 4 руды + 0,4 топлива → 3,2 металла; топливо расходуется
  полностью. Нулевой/нечисловой коэффициент производства не расходует сырьё.
- Пополнение резервов вынесено в `facility/restock.rs`: внешний покупатель
  переводит деньги владельцу рынка; перемещение собственного товара не
  требует платежа самому себе. Проверяются запас, бюджет, владелец, War/Hostile,
  переполнение; обновляются dirty-флаги. Очерёдность сервисных товаров стабильна.
- Увеличение выплаты сверх уже списанного `initial_payment` (старение/продление,
  comms/treaty bonus) оплачивает фактический заказчик — сооружение или фракция.
  Проверка предшествует всем изменениям доставки. При нехватке денег/исчезнувшем
  плательщике груз и оплата не меняются; освобождение контракта по этой причине
  не штрафует перевозчика. Добавлено событие `contract_reward_funded`.
- Изменены `facility/{mod,restock}`, `economy/recipes`, `ship/behavior`,
  `engine/{transactions,apply}` и адресные тесты; обновлены handoff и описание.
- **Проверено на Linux:** 4 новых адресных теста (включая таблицы отказов,
  фракционный и станционный бюджеты, повтор команды), 6 прежних тестов рецептов:
  **10/10**. `sim_core`/`sim_db`/`sim_server` скомпилированы при этих проверках.
  `cargo test --locked -p sim_core -p sim_server --lib supply_flow` и
  `cargo test --locked -p sim_core -p sim_server --lib economy::recipes::tests -- --skip supply_flow`.
  Использован временный target и отключена оптимизация dev-зависимостей для
  быстрой сборки; `git diff --check` выполнен. Полный набор тестов, повторный
  smoke/soak, UI и Windows-сборка не запускались по просьбе экономить проверки.
- **Граница:** это не полноценный escrow/ledger. Сохранён существующий авансовый
  дебет базовой суммы у сооружений/фракций; начальное финансирование контрактов
  населения, возврат денег при отмене/истечении, Sell/SellAll, бюджет новой
  стройки и согласованность checkpoint требуют следующего блока. Невыполнимое
  обещание выросшей награды пока может снова выбираться планировщиком.
  Дробные выпуски и бесплатное внутреннее перемещение меняют баланс темпов;
  долгосрочная устойчивость после этих изменений ещё не измерялась.
- Далее: явные денежные резервы контрактов и их возврат; проверка обеспеченности
  предложения до принятия исполнителем, затем claims/checkpoint и shadow AI.

## Что не проверено

- Для PR #1 в GitHub Actions **успешно прошли** `cargo test --locked -p sim_core` и `cargo check --locked -p client_bevy` ([первый успешный запуск](https://github.com/Mefits/Living-Sector/actions/runs/41695120507)). Это тесты кода feature-ветки, не самостоятельный Windows smoke.
- `cargo build`/запуск приложения на Windows, headless smoke и реальная работа новых UI-механик не подтверждены.
- Производительность и стабильность после тысяч дней симуляции.
- Корректность текущих сохранений оконного клиента.
- Полная воспроизводимость результатов при одинаковом seed и действиях.
- Возможность бесконфликтной синхронизации наших будущих изменений с автором.

## Статически замеченные риски (не подтверждённые runtime-баги)

- `client_bevy` и `sim_server` имеют не полностью общую последовательность выполнения тиков.
- Оконный клиент не подключает стандартный фоновый persistence-worker так же, как сервер; `Save As` не равен сохранению актуальных ECS-состояний без отдельного sync.
- Некоторые комментарии и документы описывают этапы разработки, уже изменённые в коде.
- Внутренние события ограничены журналом, полноценный причинный replay не показан.
- Наличие `world_seed` не равно доказанному детерминизму.

## Новый Observer MVP (отдельная feature-ветка)

- `feature/strategy-observer-mvp`: собственный 2D-клиент с двумя масштабами карты, движущимися кораблями, выбором реальных объектов и журналом WS-событий.
- Использует исходный headless Rust-сервер через /api/report, /api/health и /ws; HTML/CSS/JS встроены в бинарник по /observer.
- В BodySnapshot добавлено существующее `BodyIdentity.system_name`; сервер распределяет планеты по системам по имени, а не по совпадению координат.
- Добавлена проверка Node тестов адаптера и Windows preview packaging; результаты CI будут отражены в PR.
- Текущая работа **не подтверждена Windows-запуском**; не считать её завершённым интерфейсом.
