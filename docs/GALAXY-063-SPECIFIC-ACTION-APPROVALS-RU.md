# Living Sector Galaxy 0.6.3 — Предложения и конкретные одобрения ИИ

**Статус:** экспериментальный функциональный блок. Дочерняя ветка от Galaxy 0.6.2 / PR #59, которая, в свою очередь, основана на 0.6.1. Не сливать в main/stable, пока полноценный Windows CI и короткий runtime smoke на актуальном SHA не пройдут.

## Цель игрока

Игрок не командует кораблями. Он настраивает устав фракции, формулирует научные и экономические цели, а ИИ сам оценивает конкретные способы действий. Если экономический отдел находится в режиме **«Согласовывать»**, глава предлагает **одно конкретное оплачиваемое действие** и объясняет реальную стоимость и объект. Игрок может одобрить или отклонить — без прямой команды кораблю.

Пример: игрок поручил колонии местное производство электроники. Genesis проверил технологию, материалы, станцию, слот и нативную строительную альтернативу; при наличии исполнимой альтернативы игрок видит «построить завод на Mars, electronics, выбранный native action=build, оценка обязательств X CR». После одобрения проект исполняется всё теми же администраторами. Ни кнопка, ни API не создают завод сами.

## Что реализовано

1. **Нативная заявка:** \`EconomicProposal\` в \`Director.economic_proposals[faction_id]\`, с сохранением вместе с Director, отдельным read-only состоянием в \`/api/strategy.economic_proposals\`. Максимум одна открытая экономическая заявка на фракцию. Научные согласования поштучно пока не добавлены; научный review сохраняет механизм общего транша из 0.6.2.
2. **Откуда заявка:** из существующего \`options::compare_director_target\`, **только** если соответствующий вариант \`ready\`, имеет положительную цену и проходит старые проверки мандата, общего бюджета и резерва казны. Никакой второй фабрики или параллельной оценки цен.
3. **Идентичность:** ID задаёт сервер и ограничивает время принятия. Утверждение привязано к фракции, местоположению, типу мандата, товару, конкретному нативному действию, **точному** котируемому обязательству CR и сроку.
4. **Режимы:** \`pending\` → \`approved\` / \`rejected\`, после **реально оплаченного** нативного исполнения → \`consumed\`; старые заявки → \`expired\`. Отклонение не расходует CR и не разрешает оплату. Повторное нажатие запрещено движком. Старые одобрения нельзя применять к новому товару, станции или цене. Заявка хранится в сохранении; старые сейвы без заявки совместимы.
5. **API:** \`POST /api/player/economic-proposal/decision\` с \`{faction_id,proposal_id,approve}\`. Клиент *не* может передать цену, вид действия, получателя ресурсов или непосредственно оплатить обязательство. Ответ \`202 queued\` означает только очередь control engine; окончательный статус появляется из \`/api/strategy\`. Проверка Origin предназначена для локальной однопользовательской игры, не для интернета.
6. **Деньги:** принятие повышает кумулятивный разрешённый экономический транш 0.6.2 только настолько, насколько требуется конкретной заявке, но **не списывает** его и не создаёт свободных товаров. Перед нативным dispatch повторно проверяется точная цена, бюджет текущего мандата, общий budget cap, остаток казны и активность устава. Только реальный paid receipt обновляет \`EconomicMandate.spent_cr\` и \`FactionCharter.spent_economy_cr\`, после чего помечает заявку \`consumed\`.
7. **Интерфейс:** \`/observer/governance-approvals.html\`: выбор фракции, настоящая цена и объект, status, approve/reject, данные о бюджете/лимитах, последние решения главы; ссылки с остальных экранов командования.
8. **Тестирование:** \`ci/galaxy063/native_fixture_tests.py\` добавляет тест существующего ECS-мира, где первоначальное review не создаёт контракт, поддельный ID отвергается, одобрение не списывает CR, а последующий нативный исполнитель создаёт реально оплаченный водный контракт, который подтверждается \`ContractBoard\` и расходными ledger. Компактный Windows server smoke проверяет HTTP, Origin, очередь, реализацию запрета подделки. Не тратим время на ежедневные многочасовые soak.
9. **Пределы:** экономические действия \`supply\` / \`industry\` через существующую модель одного экономического мандата на фракцию. Нет десятков конкурирующих одновременно заявок, полного общего арбитража всех независимых контрактов, полноценной авторизации нескольких игроков или новой логистики.

## Гарантии и оговорки

- Одобрение лишь разрешает один нативный выбор в существующем движке, **не гарантирует** финансирование. Между предложением и обработкой могут исчезнуть ресурсы, измениться цена, пропасть маршрут или свободный слот.
- Есть отдельно «реально оплаченный контракт» и «фактически доставленная вода»/«фактическое производство». Этап 0.6.3 доказывает первый, не объявляет доставку.
- CR других автономных действий, жизнеобеспечения, зарплат, старых оплаченных проектов и корабельной экономики остаются в штатной Genesis, а не в выдуманном едином бюджетном планировщике.
- При смене цели/удалении экономического мандата его прежняя индивидуальная заявка удаляется; уже оплаченные заказы не отменяются. При изменении цены требуется новое предложение.
- Подтверждение одним кликом относится к текущему рассчитанному обязательству. Число \`quoted_commitment_cr\` — оценка выбранного нативного сравнения на момент показа, а не счёт к оплате, выставляемый фронтендом.
- Устав должен быть \`economy_authority=review\`, а экономический мандат — \`mode=delegated\`. В \`delegated\` дополнительные отдельные подтверждения не требуются, в \`autonomous\` игрок не направляет экономические цели, в \`hold\` новых поручений нет.
- В MVP одна ожидающая заявка на фракцию: новое предложение может заменить устаревшее. Это сознательно защищает от одновременного одобрения многих расходов с ещё не оплаченным резервированием. Полный multi-proposal arbiter — отдельная задача.

## Критерии готовности

1. Preflight на полном stack 0.4.1 → 0.5 → 0.6 → 0.6.1 → 0.6.2 → 0.6.3 проходит source anchors, rustfmt, JS parse.
2. Rust check; \`cargo test\` по \`galaxy06_\`, \`galaxy061_\`, \`galaxy062_\`, \`galaxy063_\`; отдельный нативный ECS fixture доказывает отказ до одобрения и paid-only успех после него.
3. Windows binary \`genesis_server.exe\`, настоящие \`/observer/governance-approvals.html\` и \`/api/strategy.economic_proposals\` доступны.
4. POST фальшивого ID лишь ставится в очередь и отклоняется в движке, не оплачивает заказ; нарушение Origin HTTP 403; старый ID не может использоваться повторно.
5. Один портативный Windows архив собирается **только после прохождения** runtime. Никаких релизов стабильной ветки и ложных обещаний завершённой тысячелетней кампании.

## Дальше

**Galaxy 0.6.4:** многокритериальная очередь альтернатив (например, «импортировать сейчас», «строить своё производство», «отложить и накопить»), обоснование ИИ по ресурсам, времени и стратегической выгоде, не только цена, с отдельной бюджетной резервацией для нескольких параллельных администраторов.

**Galaxy 0.7+:** исследовательские программы, сложная материальная T2/T3 прогрессия, дерево на столетия, исторические события и управление фракцией по принципам, а не по очереди кораблей.
