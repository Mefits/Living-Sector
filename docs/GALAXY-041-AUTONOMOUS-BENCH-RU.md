# Galaxy 0.4.1 — автономный экономический стенд

## Запуск без участия игрока

После успешной сборки Windows в workflow `.github/workflows/galaxy-ai-windows.yml`
автоматически выполняется зависимое задание **economy-soak**.

- Берёт **тот же самый** артефакт `Living-Sector-Galaxy-0.4.1-Windows`, который только что успешно скомпилирован и проверен коротким smoke-тестом. Второго `cargo build` нет.
- Использует `Genesis-Server.exe` из ZIP, настоящие данные восьми систем, новый SQLite-файл и настоящие API/WebSocket.
- Одно непрерывное игровое сохранение: **3000 → 10000 → 18000 тиков**.
- Запускает три фракции с `LIVING_SECTOR_PLANNER=hybrid`, включённым стратегическим исполнением и скоростью **x16**.
- Каждые ~600 тиков сохраняет суммарные показатели в `telemetry.csv`; отдельные полные снимки по трём контрольным точкам.
- Не запускается после мелких коммитов в `ci/galaxy041/*`: основной Windows workflow запускается только по изменениям своего workflow, входного ZIP или вручную. Один checkpoint = один комплект сборка+стенд.
- Работает на GitHub Windows runner, а не на пользовательском ПК.

## Результаты в GitHub Actions

Задание публикует артефакт **Galaxy-0.4.1-autonomous-economy-bench**.
Даже при ошибке выполнения он содержит доступные на тот момент данные:

| Файл | Содержание |
|---|---|
| `REPORT-RU.md` | Краткий русский отчёт и предупреждения; дублируется в GitHub Job Summary |
| `summary.json` | Статус, основные показатели, снимки, предупреждения |
| `telemetry.csv` | Динамика кредитов, колоний и контрактов на отдельных контрольных шагах |
| `checkpoints/t03000-diagnostics.json` | Реальные API и последние 1000 WebSocket-событий, совместимые по форме с экспортом Observer |
| `checkpoints/t10000-diagnostics.json` | То же для 10000 тиков |
| `checkpoints/t18000-diagnostics.json` | То же для 18000 тиков |
| `checkpoints/*-analysis.json` | Список строек, статус контрактов, персонал/запасы колоний, уровни денег |
| `events.jsonl` | Полный поток WebSocket-событий с момента подключения наблюдателя |
| `genesis_server.log` | Исходный журнал Windows-сервера |

## Виды автоматически обнаруживаемых симптомов

1. Голод или полное отсутствие еды на колониях, недостаток денег у домохозяйств.
2. Чрезмерное накопление CR кораблями при обнулении казн/предприятий.
3. Отсутствие новых оплаченных продовольственных доставок в течение контрольного интервала.
4. Стройки, не получавшие материалы между контрольными точками.
5. Повторяющиеся отказы `invalid_destination_stock`, `no_fuel_transfer`, `insufficient_buyer_credits` и другие причины.
6. Количество построенных зданий и активных строек на станциях, отдельно от **визуальных** слотов T1.
7. Доступность 8 систем и строго 8 межзвёздных коридоров.
8. Техническая устойчивость: API, прогресс тиков, аварии, полный жизненный цикл сервера.

**Важно:** экономический кризис отмечается как `warning`, а не объявляется успехом или техническим падением: иначе полезные диагностические артефакты будут смешиваться с падениями кода. **Hard fail** наступает на авариях, зависании тиков, недоступности API, неполных контрольных точках, потере систем/маршрутов. Стенд не доказывает глобальное сохранение CR математически; для этого остаются Rust unit-тесты реальных транзакций.

## Воспроизводимость и ограничения

Каждый прогон запускается на **свежей БД**. Мир может иметь другой случайный seed, поэтому прямое сравнение с пользовательскими t3404/t10658/t18448 — ориентир, а не строго идентичный эксперимент. Значение `world_seed` записывается в `summary.json`/телеметрию.

Три отчёта отражают **один** процесс и одну БД. Последние 1000 событий в диагностике — окно WebSocket, но в `events.jsonl` пишется весь полученный поток для количественного анализа. При разрыве WebSocket сообщения могут быть пропущены; ошибки подключения регистрируются, не маскируются.

Вся история записывается на GitHub runner, не требует открытия UI в браузере, установка пользовательского Rust/Node/Python не нужна.

Длительный прогон не повторяется по каждой правке: сначала закончить крупный пакет, затем одна контрольная сборка и длинный тест. Ветку `main`/stable не затрагивать.
